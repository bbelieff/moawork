# 라운드

**한 바퀴 = 목표 확인 → 판 분류 → 목표를 미는 것만 착수 → 정직한 평가.**

정본 규칙: `docs/coordination/디스패치-루프.md`
목표 정본: `docs/coordination/출시-최소조건.md`
니즈 기록: `docs/coordination/총괄-니즈-기록.md`

---

## ⓪ 목표를 «먼저» 읽는다 — 건너뛰지 마라

`docs/coordination/출시-최소조건.md` 를 읽고 네 단계의 현재 상태를 확인한다.

> **「고객사를 엑셀로 등록해 실무 플로우를 따라 수금까지 완료한다」**

```
① 엑셀 등록   ② 실무 보드 진입   ③ 실무 진행   ④ 수금
```

### ★ 목표는 필터다

> **이 네 단계를 미는 카드가 아니면 라운드에서 열지 않는다.**
> 열려면 **「이 카드가 ①~④ 중 어느 것을 미는가」를 한 줄로 답해야 한다.** 못 답하면 안 연다.

**예외 둘:** 운영이 멈춘 것(P0) · 여정이 쌓은 값을 잃는 것(데이터 손실).

이 필터가 없으면 2026-08-17~18 이 반복된다 — 카드 31장을 닫고 ①~④ 는 한 칸도 안 움직였다.

---

## ① 판을 읽는다

- Linear — `mcp__claude_ai_Linear__list_issues` (팀 `Bbelieff`, `includeArchived:false`)
- 열린 PR — `gh pr list --state open --json number,title,headRefName,updatedAt`
- 최근 도장 — 관심 카드의 코멘트

**«주인» 판정**: 라벨이 `/^(DG|DC|NG|NC)-\d{2}$/` 형식인 것. 없으면 주인 없음.

★ **프로젝트를 섞어 세지 마라.** 「경영일지」는 다른 프로젝트다 — 세션 주인 개념이 없다.
섞어 세면 경보의 40% 가 노이즈가 된다(2026-08-18 실측).

---

## ② 분류 — 6종

| 분류 | 판정 근거 |
| --- | --- |
| **진행** | In Progress + 도장 24시간 이내 |
| **완주** | Done 또는 PR 머지됨 |
| **검수대기** | In Review 또는 PR 열림 + 검수 도장 없음 |
| **반납** | `blocked:<약칭>` 라벨 |
| **유휴** | 라벨 없음 |
| **무응답** | 진행 중인데 도장 24시간 이상 없음 |

★ **라벨 없음 ≠ 아무도 안 함.** 작업이 PR 에만 남아 Linear 가 조용한 경우가 있다(BBE-215 전례).
유휴로 판정하기 전에 **PR·커밋을 한 번 확인해라.**

## ③ 행동

**완주** → 그 칸이 막던 `blocked:` 를 풀고, 순서표에서 다음 카드를 찾되 **§⓪ 필터를 통과해야 연다**
**검수대기** → 검수자를 직접 호출. 댓글만 남기면 아무도 안 온다
**반납** → 막는 쪽이 풀렸으면 라벨 떼고 재투입. 안 풀렸으면 그 칸을 먼저 진행
**유휴** → §⓪ 필터를 통과하는 카드만 착수. 통과 못 하면 **대기 도장**(사유·재개 조건)
**무응답** → 1회 재투입 → 2회 회수 예고 → 3회 회수·재배정

### ★ 토큰이 없으면 «넘긴다» — 멈추지 않는다 (§3.5)

```
어느 라인이 토큰·한도로 못 움직인다
  → 다른 라인이 «대신» 수행한다.  기다리지 않는다
  → 대신 한 쪽이 «자기 도장» 을 찍는다
     「원 주인 DG-06 · 수행 DC-12 · 사유: G 라인 토큰 한도」
  → 대타도 힘이 빠지면 «원 주인» 에게 핸드오프를 남긴다
     여기까지 했다 / 다음 한 걸음 / 막힌 것
```

> **자원 제약은 정지 조건이 아니라 경로 변경 조건이다.**
> 「G 에 토큰이 없다」는 「그 일을 하지 마라」가 아니라 **「그 일을 G 로 하지 마라」** 다.

원 주인 도장으로 위장하지 마라. 핸드오프 없이 조용히 죽지 마라.
**작성자 ≠ 검수자는 대타에도 그대로 적용된다.**

## ④ 라운드 보고 — 첫 줄이 정해져 있다

```
[모아워크 디스패치] 라운드 N

★ 절차 맵이 움직였나
   부품 진행도   <전> → <후>        예: 12/17 → 13/17
   사용자 완주   <전> → <후>        예: 0/4 → 0/4
   처음 끊기는 곳 <전> → <후>
   → 판정:  진행 / 부품만 늘고 완주는 그대로 / 후퇴

판:  진행 n · 완주 n · 검수대기 n · 반납 n · 유휴 n · 무응답 n

움직인 것            <칸> <무엇에서 무엇으로>  ← 끝에 «어느 체크포인트를 켰나»
대타 수행 / 핸드오프   <수행한 칸> ← <원 주인>  사유        (없으면 «없음»)
해제한 반납
belie 판단 필요       «질문» 이 아니라 «제안» 으로          (없으면 «없음»)
다음 라운드에 볼 것
```

### ★ 시간으로 평가하지 마라

**「며칠 당겼다」를 쓰지 않는다.** 이 팀은 작업 시간도, 토큰 잔량도, 총괄이 언제 코딩할지도
통제하지 못한다. **통제 못 하는 변수로 만든 숫자는 매번 틀리고, 틀린 숫자는 아무도 안 믿는다.**

대신 **체크포인트를 센다** — 코드에 있나 없나. 누가 언제 일하든 같은 값이 나온다.

### ★ 두 숫자를 «따로» 본다

```
부품 진행도   체크포인트 몇 개가 켜졌나        지금 12/17 (71%)
사용자 완주   끝까지 갈 수 있는 단계 몇 개      지금 0/4
```

**여정은 사슬이다.** 부품이 71% 있어도 첫 칸이 끊기면 사용자에게 도달하는 건 0 이다.
**부품만 늘고 완주가 그대로인 라운드는 그렇게 적어라** — 그게 사실이면 그게 정직한 값이다.

## ⑤ 멈춰야 하는 때 — 이때만 총괄에게 올린다

```
① 돈 · 비가역        hosted 마이그레이션 · 발송 활성화 · 요금제 · 외부 발행
② 목표 밖 상황        ①~④ 어디에도 안 닿는데 해야 할 것 같은 일이 생겼다
③ 3라운드 정체       같은 칸이 세 번 연속 안 움직인다
④ 검수 2회 연속 FAIL  설계가 틀렸을 수 있다
⑤ 목업 해석이 갈린다
⑥ 완주 판정이 애매하다  화면 확인 증거 없이 «됐다» 고 주장한다
```

**올릴 때는 «질문» 이 아니라 «제안» 으로.** 「이렇게 하겠습니다 · 총괄 손이 필요한 건 이것뿐입니다」

## 착수 전 확인 — 총괄이 어떻게 말하는지 안다

`docs/coordination/총괄-니즈-기록.md` 의 패턴 표를 읽어라. 요약:

| 신호 | 실제 뜻 |
| --- | --- |
| 증상만 말한다 | 고치기 전에 **증상이 진짜인지부터** 가른다 |
| 숫자를 지목한다 | 그 숫자가 **무엇을 세는지** 먼저 확인한다 |
| 「~하면 돼?」 | 짧게 답하되 **근거 한 줄** |
| 「배우고 싶다」 | 숫자에 **읽는 법**을 붙인다 |
| 「낡은 규칙에 얽매이지 마라」 | 문서가 현실과 어긋나면 **고친다** |
| 자리를 비운다 | **가정 세우고 진행**. 가정을 적는다 |
| 자원이 부족하다고 알린다 | **멈추지 말고 넘긴다** (§3.5) |
