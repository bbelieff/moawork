## 5. 업무상 이유(암묵지) — 확인된 것 / 추론 / 미확인 구분

### ✅ 문서·구조로 확인된 것
1. **상태값이 곧 작업 대기열이다.** 그룹 14개가 상담 상황 라벨과 1:1로 대응한다. 담당자는 "상태를 바꾸는 것"만으로 아이템이 해당 대기열로 이동한다 — **수동 정리 노동을 자동화로 대체**한 구조.
2. **인계 지점이 명시돼 있다.** 컬럼 설명 "[인계]로 변경하면 [컨텍관리]로 넘어갑니다" = 신규고객 → 컨텍관리 보드로 넘기는 **공식 핸드오프 트리거**.
3. **제조업은 별도 트랙이다.** 일반 "1차/2차 부재"와 별개로 "제조업 1차/2차 부재" 라벨·그룹이 따로 있다. 제조업 리드를 다르게 관리한다는 뜻(뷰 "제조업DB"도 별도 존재).
4. **담당자별 물리적 분리.** 피드백 완료 시 담당자에 따라 서로 다른 그룹으로 보낸다 → 담당자가 자기 그룹만 보면 되게 만든 운영.

### 🟡 구조로부터의 추론 (belie 확인 권장)
5. **부재 관리가 정교하다.** "1번~4번 부재"·"1일 1회 전화" 라벨과 `📬` 메시지 컬럼들이 존재 → 부재 횟수별 단계적 접촉 규칙이 운영되는 것으로 보인다.
6. **"보류/고민/다시 상담"이 분리된 이유** = 재접촉 시점이 서로 달라서로 추정(즉시/중기/장기).

### ❌ 미확인 (실측으로 알 수 없음)
7. `📬` 자동화 5건이 실제로 무엇을 하는지(알림/발송/구독).
8. 각 라벨의 **SLA·재접촉 주기**(며칠 뒤 다시 전화하는지).
9. 상태 전환의 **비공식 규칙**(예: 몇 회 부재 후 거절 처리하는지).

먼데이에 **부재 1번 → 2번 → 3번 → 4번**이라는 단계가 있는데, 그걸 옮길 때 두 갈래가 있었다.

```
(가) 시스템이 자동으로 올린다   1번 찍고 3일 지나면 → 자동으로 2번
(나) 사람이 직접 올린다        전화 걸고 안 받으면 → 담당자가 2번으로 바꿈
```

(가)면 «며칠»이라는 숫자를 코드에 넣어야 해서 그 값을 물은 것이다.
**답이 (나)로 나왔다** — 자동 승급은 만들지 않는다. 대신 **다시 걸 날짜를 달력으로 적고, 그날이 오면 알림**이 간다.
이쪽이 더 낫다: 고객마다 사정이 달라서 «3일»이라는 하나의 숫자가 맞을 리 없다.

### 7-4. 남은 미상 — 수신 URL

**수신 엔드포인트 URL은 monday 쪽에서 확인 불가.**
- API `webhooks` 쿼리는 url 필드를 노출하지 않는다(config 에 columnId 만).

- legacy automation 이라 ⋯ 메뉴에서 편집·조회가 막혀 있다.

→ **수신 측에서 확인해야 한다.** 확인 경로: 자동화를 만든 계정(userId 48302352)이 연결한 외부 서비스
(자동화 도구 / 메시지 발송 서비스 / 자체 서버) 의 연동 설정.

### 7-5. 모아워크 설계 시사점

1. `board_automation_rules` 에 **아웃바운드 웹훅 액션 유형**이 필요하다. 그룹 이동만으로는 5건을 표현 못 한다.
2. 발송은 앱 프로세스가 아니라 **worker(pg-boss)** 에서 재시도·지수백오프와 함께 처리한다.

   화면·로그에는 도메인과 성공/실패만 남긴다.
4. 실행 기록 화면이 함께 있어야 한다(먼데이의 「실행 기록」 탭 대응). 위 14회 조회가 그 형식의 근거다.
