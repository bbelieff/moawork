# 종합 진단 — 왜 많이 만들었는데 화면이 안 나오나

**2026-08-12 · 작성 MW-총괄 · 요청 belie**
**대상 실측: `origin/main` 최근 40커밋 (2026-08-09 ~ 08-12) · 코드 실측이지 인상이 아니다**

---

## 0. 한 줄

세 가지 증상(중복·회귀·화면 안 나옴)은 **서로 다른 문제가 아니다.**
전부 **「완료」의 정의가 «코드가 있다» 로 되어 있고, «화면이 그렇게 보인다» 가 아니기 때문**이다.

## 2. 근거 A — 만든 것의 **1.8%** 만 사용자가 보는 화면이다

`origin/main` 최근 40커밋, 추가된 29,688줄의 행선지:

```
 10,499줄  35.4%  문서 · 설계
  5,994줄  20.2%  테스트
  5,453줄  18.4%  DB 마이그레이션
  4,837줄  16.3%  계약 · 서버 로직
  1,339줄   4.5%  화면 부품 (components/)
  1,042줄   3.5%  설정 · 잠금파일
────────────────────────────────────
    524줄   1.8%  ★ 사용자가 보는 화면 (page.tsx · layout.tsx)
```

**화면 관련 전체를 다 합쳐도 6.3%다.** 문서가 화면의 **20배**로 쌓였다.

이건 게으름이 아니다. **각 세션이 시킨 대로 한 결과다.**
프롬프트가 「계약을 만들어라 · 테스트로 증명해라 · 도장을 찍어라」였고, 전부 그렇게 했다.
**「화면에 나오게 해라」가 완주 조건에 없었다.**

## 3. 근거 B — 목업과 앱을 잇는 검사가 **0건**이다

이게 ③번 증상의 직접 원인이다.

```
qa-mockup.mjs 가 읽는 파일   →  UI목업_워크스페이스_최종_v6.html  (목업 자기 자신)
앱 코드를 읽는 부분           →  없음
scripts/check.sh 에서 실행    →  0회 (아예 안 돈다)
```

**즉 「86/86 통과」는 «목업 파일이 목업답게 생겼다» 만 증명한다.**
앱이 목업과 같은지는 **아무도, 어떤 방법으로도 확인하지 않는다.**

그런데 모든 세션이 착수·완주 도장에 「목업 86/86 PASS」를 근거로 적고 있다.
**전원이 성실하게, 아무것도 증명하지 않는 검사를 통과시켜 왔다.**

앱 소스에서 목업을 언급하는 13개 파일도 전부 **주석**이다 (`// UI목업_워크스페이스_최종_v6 기준`).
주석은 검사가 아니다.

### 구조 자체도 어긋나 있다

```
목업 정본  탭 6개짜리 «화면 1개»
           신규리드 관리 · 리드컨택 관리 · 계약업체 실무
           업체관리 현황 · 공지사항 · 프리셋 라이브러리

실제 앱    독립 라우트 25개
           /newcust · /work · /boards · /deals · /companies
           /contract · /notices · /dash/* · /settings/* ...
```

목업은 **한 화면 안에서 탭으로 넘나드는 구조**인데, 앱은 **주소가 다른 별개 페이지들**이다.
이건 버그가 아니라 **아무도 이 차이를 판정할 근거를 갖지 못했기 때문**에 생긴 표류다.

## 4. 근거 C — 파일 **52개**가 어느 화면에도 닿지 않는다

화면 진입점(page·layout·route) 78개에서 import 를 따라가며 도달 가능한 파일을 세었다.

```
진입점에서 닿는 파일     306개
아무 화면에도 안 닿는 파일  52개   ← 테스트 제외 전체의 15%
```

몰린 곳: `lib/accounting` 5 · `lib/messaging` 4 · `lib/perf` 4 · `lib/policyfund` 4 ·
`components/accounting` 2 · `components/boards` 2 …

**세션들은 이걸 알고 있었고, 정직하게 보고했다.** 노트북 GT04 의 도장:

> 현재 main 에서 `DealLedgerPanel`·`LedgerExportButton` 을 소비하는
> 기존 화면 조합 import 는 **0**입니다. … 실제 업무 상세 화면 노출을 주장할 수 없습니다.

**보고는 완벽했다. 받아서 조치할 사람이 없었을 뿐이다 — 그건 나다.**

## 5. 근거 D — 중복 8건은 «리스 제도» 의 구조적 결과다

충돌을 막으려고 **파일 단위 리스(lease)** 를 도입했다. 그건 잘 작동했다 — 파일 충돌은 거의 없었다.
그런데 **배정은 카드 단위**였다. 두 단위가 어긋난다.

같은 카드를 C진영·G진영에 각각 주면 → 서로 다른 파일을 잡으므로 **리스는 안 겹친다**
→ 그러나 **결과물은 같은 것을 두 번 만든 것**이다.

| 카드 | C진영 | G진영 | 결과 |
| --- | --- | --- | --- |
| BBE-116 로고 | #130 | #152 ✅머지 | #130 폐기 |
| BBE-122 권한 | #125 | #157 ✅머지 | #125 폐기 |
| BBE-119 부서 | #123 | #154 ✅머지 | #123 폐기 |
| BBE-19 원장 | #110 | #158 ✅머지 | #110 폐기 |
| BBE-14 보드 | #146 | #153 ✅머지 | #146 폐기 |
| BBE-18 대시보드 | #147 ❌닫힘 | #156 ✅머지 | #147 폐기 |
| BBE-104 자동화 | #122 ❌닫힘 | #151 ✅머지 | #122 폐기 |
| BBE-20 자동화실행 | #148 ✅머지 | #159 열림 | 중복 진행중 |

**8개 카드 · PR 8건 폐기.** 세션이 잘못한 게 아니라 **내가 같은 카드를 두 번 발주했다.**

원인: 「40칸을 놀리지 말자」를 목표로 삼았다. **처리량을 늘리려다 중복을 만들었다.**

## 6. 근거 E — 회귀는 「화면 확인 없이 머지」의 필연이었다

오늘 P0 (`/workspace-entry?error=routing`, 오너가 제품 진입 불가) 의 이력:

```
PR #160  BBE-89  비인가·비멤버 라우팅 통일
  CI          ✅ 통과
  단위 테스트  ✅ 451줄 추가, 전부 통과
  독립 검수    ✅ PASS
  화면 확인    ❌ NOT_RUN
  결과         사장이 자기 제품에 못 들어감
```

바뀐 건 **막히는 조건이 아니라 「막혔을 때 어디로 보내는가」** 였다.
전에는 로그인·회사 고르기로 보내 빠져나올 길이 있었는데, 지금은 이유도 안 알려주는 막다른 방으로 보낸다.

**단위 테스트로는 절대 안 잡힌다.** 각 함수는 정확히 «설계대로» 동작한다.
잡히는 방법은 하나뿐 — **사람이 그 주소를 열어보는 것.**

그리고 그걸 건너뛰어도 되게 만든 건 **내가 만든 한시 규칙**이다:

> `docs/playbooks/subagent-review.md` — 스크린샷·health 는 **NOT_RUN** 으로 명시하고 **머지를 막지 않는다**

의도는 옳았다(`app/.env.local` 이 없어 못 찍으니까). **효과는 화면 검증 전면 중단이었다.**

## 7. 종합 — 세 증상의 공통 뿌리

```
                    완료 = «코드가 있고 테스트가 통과한다»
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
     화면이 완주 조건이         화면 확인이           같은 «완료» 를
     아니므로 아무도             선택 사항이므로        두 진영이 각각
     조립하지 않는다             회귀가 통과한다        달성해 버린다
              │                     │                     │
              ▼                     ▼                     ▼
        ③ 화면 안 나옴          ② 회귀                ① 중복
```

**제도가 만든 결과지, 세션의 실력 문제가 아니다.**
실제로 오늘 잡힌 결함 4건은 전부 **세션들이 스스로 잡아서 정직하게 보고한 것**이다.
멱등키 결함(GT10)·D44 오탐 자백·정본 파일 부재(CT03)·조립 미완 자진신고(GT04).
**보고 품질은 높다. 그 보고를 받아 방향을 트는 쪽이 못 따라갔다.**

## 8. 내 책임 — 구체적으로

1. **목업↔앱 검사를 안 만들었다.** 목업만 86개까지 다듬고, 정작 «앱이 저것과 같은가» 는 비워뒀다
2. **NOT_RUN 예외를 내가 열었다.** 화면 검증이 사라진 직접 원인
3. **카드 단위 배정 + 파일 단위 리스**의 어긋남을 알고도 방치했다
4. **「40칸 다 쓰자」를 목표로 삼았다.** 병목은 만드는 속도가 아니라 «조립과 확인» 이었는데 반대로 눌렀다
5. GT04 의 「소비자 0」 보고를 **읽고도 카드로 만들지 않았다**

## 9. 처방 — 5가지. 순서대로 한다

### ① 완료의 정의를 바꾼다 (즉시 · 전 세션)

```
지금:  코드 + 테스트 + CI = 완주
바꿈:  코드 + 테스트 + CI + 「그 화면 주소를 열어 눈으로 본 증거」 = 완주

화면이 없는 계약·라이브러리 카드는 «완주» 가 아니라 «부품 납품» 이다.
부품만 낸 카드는 반드시 «어느 화면이 이걸 쓰는가» 를 후속 카드로 남긴다.
소비자 없는 부품은 만들지 않는다.
```

### ② 목업↔앱 검사를 만든다 (최우선 신규 카드)

`qa-mockup.mjs` 는 목업만 본다. **앱을 보는 짝을 만든다.**

```
docs/design/qa-app.mjs   (신규)
  ├ 목업에서 탭·아이템·컬럼·타입·이동규칙을 뽑는다  (dump-mockup 재사용)
  ├ 앱의 프리셋·컬럼 정의에서 같은 것을 뽑는다
  └ 다르면 FAIL. 무엇이 몇 개 다른지 숫자로 낸다

scripts/check.sh 에 넣는다 — 그래야 아무도 못 건너뛴다
```

이게 없으면 나머지 처방은 다 말에 그친다. **이것이 0번 관문이다.**

### ③ 「조립」을 소유하는 자리를 만든다

지금은 부품 만드는 세션만 있고 **끼우는 세션이 없다.**

```
신설: 조립조 (세션 3칸)
  일: 고아 파일 52개를 화면에 연결한다
      목업의 «탭 6개짜리 한 화면» 구조를 실제 라우트로 세운다
  권한: 다른 세션의 리스를 넘어 page.tsx·layout.tsx 를 고칠 수 있다
       (조립은 본질적으로 남의 부품을 만지는 일이다)
```

### ④ 카드 소유를 단일화한다

```
한 카드 = 한 세션. 예외 없다.
같은 카드를 다른 진영에 주려면 «앞의 것을 취소한 뒤» 준다.
Linear 카드에 「담당 세션」을 적고, 없는 카드는 착수 금지.
```

### ⑤ 세션 수를 줄인다 — 40 → 15 안팎

불편한 얘기지만 숫자가 그렇게 말한다.

```
지금 병목:  만드는 속도가 아니다. 조립·검증·조율이다
40칸 운영의 실제 비용:  중복 8건 + 조율 문서 10,499줄 + 리스 협상
```

**칸을 줄이고 남는 인력을 조립조·검증조로 돌린다.**
15칸이 40칸보다 «화면» 을 더 많이 낸다. 오늘 데이터가 그걸 보여준다.

## 10. 지금 당장의 순서

```
1. P0 회귀 revert  (#160)                    ← 진행 중
2. qa-app.mjs 만들기 + check.sh 에 편입       ← 새 0번 관문
3. 중복 PR 8건 정리 (닫기)
4. 조립조 3칸 세우고 고아 52개 연결 착수

```

**2번 전까지는 화면 관련 카드를 새로 발주하지 않는다.**
재는 자가 없는 상태에서 더 만들면 어긋남만 늘어난다.

## 11. 기록해 둘 것

- 결정대장에 **D76~D80** 으로 위 처방 5가지를 등재한다
