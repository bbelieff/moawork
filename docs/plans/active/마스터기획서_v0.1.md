```
[Phase 0. 준비] ─ [Phase 1. MVP 개발] ─ [Phase 2. 확장] ─ [Phase 3. 플랫폼화]
      ▲
   지금 여기 (기획서 v0.1 = Phase 0의 첫 산출물)
              └ 이번 세션: "정책자금 CRM" → "통합관리시스템" 리브랜딩·확장
```

**이 문서를 왜 새로 쓰나요?(초보자용 위치 설명)**
지난 세션까지 만든 것은 "정책자금 컨설팅용 CRM"이었습니다. 그런데 그 안을 들여다보니 이미 영업만이 아니라 실무·정산·성과·세금까지 다루고 있었습니다 — 즉 실체가 이미 "CRM"보다 큽니다. 그래서 **이름과 뼈대를 실체에 맞게 격상**한 것이 이 문서입니다. 바뀐 건 "무엇을 어떻게 묶어 보여주는가(정체성·구성·화면 구조)"이고, **이미 확정한 기술·정책·MVP 범위는 그대로**입니다.

이 문서의 역할: ① 결정된 것 고정 ② 미정인 것 목록화 ③ 만들 것(범위) 확정 ④ 만드는 순서(로드맵) 확정.

# PART A. 제품 정의 (리브랜딩)

## A-1. 한 줄 정의

**"먼데이의 자유도 + 토스의 쉬움으로, 5인 이하 전문서비스 조직의 영업–실무–정산–성과를 한곳에서 굴리는 통합관리시스템"** (1호 특화: 정책자금 컨설팅).

- 이전 정의(CRM v0.1): "…정책자금 업무 특화 **영업관리 CRM**."
- 바뀐 점: 제품 정체성이 "영업 도구(CRM)" → **"조직 운영 전반을 묶는 통합관리시스템"**으로 격상. CRM은 사라지지 않고 **그 안의 1번 기둥(영업·고객)**이 됨.

## A-2. 타겟 (변경 없음)

| 구분 | 내용 |
|---|---|
| 주 타겟 | **정책자금 컨설팅 업체** (1호 업종 모듈) |
| 부 타겟 | 보험GA·세무사·변리사·행정사 등 5인 이하 전문서비스 조직 |
| 조직 규모 | 1~5인 중심 (과금 티어 1~3 / 4~7 / 8~10 / 11~) |
| 핵심 차별점 | 계약 이후(실무·수납·사후관리)까지 한 시스템 + 홈택스 연동 + 조직 성과관리 |

## A-3. 리브랜딩·확장 요약 (Before → After)

| 관점 | Before (신규 CRM v0.1) | After (통합관리시스템 v0.1) |
|---|---|---|
| 정체성 | 정책자금 특화 **영업관리 CRM** | 전문서비스 조직 **통합관리시스템** |
| 상위 구성 | 5단계 파이프라인 중심 | **6개 기둥**(아래 A-4)으로 재편, 파이프라인은 1번 기둥 |
| 화면 뼈대(IA) | 파이프라인·업체관리·정산·대시보드·설정 | 기둥별 IA로 재편(PART H) |
| 확정 기술·정책 | D1~D13 | **동일**(그대로 이월) — 리브랜딩은 기술을 바꾸지 않음 |
| MVP 범위 | 코어+홈택스+알림톡+성과+정책자금팩 | **동일** — 이름이 커졌다고 만들 것이 늘지 않음(가드레일: J-9) |
| 데이터 모델 | PART G 테이블 | **동일** — 6기둥은 대부분 기존 테이블 재사용 |

> **핵심**: 이번 변경은 **"재포장·재배치·재명명"**이지 **"기능 추가"가 아닙니다.** 새 기둥에 담기는 실무/정산/성과는 이미 있던 것들의 승격이고, 진짜 신규 기능은 전부 Phase 2/3로 못 박습니다(스코프 인플레이션 방지 — PART J-9).

## A-4. 통합관리 6기둥 (제품의 새 뼈대)

```
① 영업·고객 관리      (기존 CRM 코어)         마케팅→미팅→계약 파이프라인·고객사·활동기록
② 실무·프로젝트 관리   (계약 이후 실행)         기관접수→심사→승인, 서류·마감·담당배분
③ 정산·회계           (돈의 흐름)             수수료 계산·수납·세금계산서·매출/미수 현황
④ 성과·조직           (사람·동기부여)          인센티브·리더보드·활동량·권한·초대
⑤ 문서·자동화·연동     (시스템의 배관)          계약서/서류함·알림톡·홈택스·상태트리거
⑥ 업종팩             (특화 프리셋)            정책자금 1호(진행기관·세부자금·지역·수식)
```

이 6기둥이 **모듈 맵(PART E)**과 **화면 구조(PART H)**의 기준이 됩니다. 기둥은 "보여주는 묶음"일 뿐, 데이터는 대부분 공유(PART G).

## A-5. 기존 자산과의 관계 (변경 없음)

- **서울경영지원센터 먼데이 워크스페이스** = 도메인 지식 원천. 파이프라인·컬럼·선택지(진행기관 15종·세부자금 53종·지역)를 업종팩 프리셋으로 재활용.
- **기존 먼데이 데이터(신규고객 8,400건 등)**: 이관 안 함(확정). 패턴만 샘플링해 **현실적 더미 시드** 생성. 실제 고객명 사용 금지.
- **경영일지(별도 제품, 제작 중)**: 개인 기록 중심 — **여전히 별개 제품**. 통합관리시스템에 합치지 않음. 추후 연동만 검토(Phase 3 백로그).

# PART J. 리스크 & 비판적 의견 (솔직 버전)

1. **외부 계약이 개발보다 느리다** — CODEF류(기업 심사)·카카오 발신프로필·팝빌 모두 리드타임 존재. 코드보다 먼저 Phase 0에서 신청. 안 하면 MVP 완성 후 몇 주를 놀게 됨.
2. **"고객의 고객" 정보 취급** — 홈택스 위임 수집은 고객사의 고객(사업자) 개인정보 수탁 구조. **전자 동의서 + 개인정보 위수탁 문구**가 제품 기능이어야 함(법무 검토 1회). 귀찮은 게 아니라 영업 무기("동의·증적 자동관리").
3. **알림톡 규제** — 정보성/광고성 구분, 광고성은 사전 수신동의·야간제한. 부재/미팅/입금 안내는 정보성으로 설계. 템플릿 반려 대비 문구 2안씩.
4. **MVP가 여전히 크다** — 홈택스+알림톡+성과 3모듈 동시는 5인 이하 팀 기준 공격적. 권장 순서: core → notify → perf → hometax(조회) → hometax(발행). 발행은 MVP 말미로 밀려도 치명적이지 않음.
5. **RLS 실수 = 남의 조직 데이터 노출** — 멀티테넌트 최대 사고 지점. 스프린트마다 "다른 조직으로 접근 시도" 자동 테스트 고정.
6. **먼데이급 자유도의 유혹** — "컬럼타입 하나만 더"가 반복되면 Phase 3를 앞당김. 커스텀필드 타입은 O11 밖 추가 금지(기획서 개정으로만).
7. **구글 로그인 단일(수용됨)** — 구글 계정 없는 소상공인 존재. 저항 시 카카오 추가는 Supabase에서 작업 적음 — 후순위 백로그.
8. **상표/제품명** — 결정 전 키프리스 상표검색 필수. 도메인 선점과 함께.
9. **⭐리브랜딩발 스코프 인플레이션(이번 세션 최대 신규 리스크)** — "통합관리시스템"이라 부르는 순간 "그럼 회계도·프로젝트관리도·자동화도 다 되어야지" 기대가 커진다. **이름이 커져도 MVP는 D9 그대로.** (신규) 모듈은 Phase 2/3에 못 박았고, 이 경계를 넘는 요청은 기획서 개정으로만 허용. A-3·E-1의 ✅ 표시가 유일한 "만들 것" 기준.
10. **⭐"통합관리시스템"은 좋은 시장 브랜드가 아니다** — 일반명사라 상표 등록·검색 노출·차별화에서 불리. **내부 카테고리명으로만 쓰고, 판매용 고유 브랜드(O1)를 별도로.** 지금 문서·폴더·코드에서 이 이름을 쓰는 건 괜찮지만 간판으로 굳히지 말 것.
11. **광고 리드 인입도 리드타임·동의가 필요** — 메타 리드애즈 웹훅은 Meta 앱 권한(`leads_retrieval`)·페이지 **Lead Access 승인**(검수 리드타임)이 필요. 광고로 들어온 리드도 **개인정보 수집·이용 및 (연락 시) 수신 동의 근거**가 있어야 함 → 광고/랜딩폼 동의문구를 제품이 기록. Zapier는 먼데이 병행기의 임시 다리일 뿐이며, 모아워크는 이 인입을 **코어로 내장**(제품 존재 이유, D15). ※이는 의도된 MVP 확정 추가이지 스코프 크리프가 아님(D9 개정).
