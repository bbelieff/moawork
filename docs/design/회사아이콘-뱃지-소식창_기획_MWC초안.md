## 0. 세 요청이 사실 하나의 문제다

belie가 준 3건은 따로 보이지만 **"내가 지금 어디에 있고, 무엇이 달라졌는가"** 라는 한 질문의 세 부분입니다.

```
회사 아이콘  →  나는 지금 [어느 회사]에 있나        (공간 인지)
업데이트 뱃지 →  [무엇이] 달라졌나                  (변화 감지)
소식창       →  [왜·누가] 그렇게 했나               (맥락 이해)
```

그래서 셋을 **같은 축(회사 = 공간)** 위에 얹어야 일관됩니다. 스위처 확정안(D-S1: 좌상단 = 공간)이 이미 그 자리를 잡아뒀으니, 아이콘은 그 자리에, 뱃지는 그 옆에, 소식창은 그 연장선에 둡니다.

# A. 회사 아이콘 (표식)

## A-1. 기본 원칙 — 업로드는 선택, 표식은 항상 있다

이미지가 없어도 **빈 네모가 보이면 안 됩니다.** 3단 폴백:

```
① 업로드 이미지          (오너·관리자가 올린 로고)
② 없으면 → 이니셜 마크    ("서울경영지원센터" → 서)  + 회사명 해시로 자동 배정된 브랜드 색
③ 그것도 불가 → 기본 심볼 (MoaWork 마크)
```
- 자동 색은 **브랜드 v1.0 팔레트 안에서만** 뽑습니다(Blue/Teal/Violet + 파생 톤). **People Coral 금지**(담당자·멘션 전용).
- 이니셜은 한글 1자 / 영문 2자. 이모지·특수문자는 제거 후 첫 글자.

## A-2. 업로드 스펙

| 항목 | 값 | 이유 |
|---|---|---|
| 형식 | PNG · JPG · SVG · WebP | SVG는 **정제 후 저장**(스크립트·외부참조 제거 필수 — XSS) |
| 최대 용량 | 2MB | |
| 권장 크기 | 512×512 이상 정사각 | 다운스케일이 업스케일보다 안전 |
| 업로드 UX | 드래그&드롭 + 파일선택, **정사각 크롭 후 확정** | 비율 깨짐 방지 |
| 저장 | Supabase Storage `org-icons/{org_id}/{hash}.webp` | 원본 대신 **WebP 3종(32/64/256px) 리사이즈 저장** |
| 접근 | 비공개 버킷 + 서명 URL(만료) | 기존 파일 정책과 동일 |
| 권한 | **오너·관리자만** 변경 | 멤버는 조회만 |
| 삭제 | 언제든 제거 → ② 이니셜로 복귀 | |

## A-3. 어디에 나타나는가 (한 번 바꾸면 전부 반영)

좌상단 스위처 트리거 · 스위처 목록 각 행 · 진입 화면(`/workspace-entry`)의 회사 카드 · 알림/소식 항목의 발신 회사 · 브라우저 파비콘은 **모아워크 고정**(회사별 파비콘 금지 — 제품 정체성 유지).

## A-4. 안전장치
- 업로드 이미지는 **콘텐츠 검증**(실제 이미지인지 매직넘버 확인). 확장자만 믿지 않음.
- 회사 아이콘이 **모아워크 로고와 혼동될 정도로 유사**해도 막지 않되, 제품 상단바의 MoaWork 워드마크는 항상 별도 유지.

# B. 업데이트 뱃지

## B-1. 가장 중요한 원칙 — 뱃지는 아껴야 힘이 있다

5인 이하 조직에서 뱃지가 남발되면 **1주일 만에 무뎌지고 아무도 안 봅니다.** 그래서 규칙을 먼저 못박습니다.

> **뱃지는 "내가 해야 할 일"에만 숫자를 준다. 나머지는 점(dot)이거나 없음.**

| 종류 | 표시 | 대상 | 예 |
|---|---|---|---|
| **액션 필요** | 🔴 **숫자** | 나에게 배정·요청·멘션된 것 | 가입 요청 승인 3, 나에게 배정된 딜 2, 멘션 1 |
| **변화 있음** | • **점(무채색)** | 내가 안 본 변화가 있는 영역 | 업무관리에 새 글, 공지 1건 |
| **정보** | 없음 | 남이 한 일반 활동 | 다른 담당자의 단계 이동 |

## B-2. 어디에 붙는가

```
좌상단 회사 스위처   → 【다른 회사】에 액션 필요 건이 있을 때만 숫자
  └ 목록의 각 회사행 → 그 회사의 액션 필요 수
사이드바 메뉴 항목   → 그 영역의 액션 필요 수(숫자) 또는 미확인 변화(점)
상단바 🔔 벨         → 내 알림 미읽음 수(숫자)        ※벨은 이미 존재, 내용만 비어 있음
```

**핵심**: 다른 회사의 뱃지를 스위처에 올리면, **회사를 안 열어도 "저기 뭔가 있다"를 안다** → belie가 원한 "협업자·사용자가 변경 사실을 안다"가 최소 비용으로 달성됩니다.

## B-3. 읽음 처리 규칙 (모호하면 안 되는 부분)

| 상황 | 처리 |
|---|---|
| 알림 항목을 **열었다** | 그 항목만 읽음 |
| 해당 화면에 **들어갔다** | 그 영역의 **점**은 사라짐. **숫자(액션 필요)는 유지** — 실제로 처리해야 사라짐 |
| "모두 읽음" 버튼 | 점만 일괄 제거. 액션 필요 건은 **제거되지 않음** |
| 다른 기기에서 읽음 | 서버 기준 동기화(계정 단위) |

> 이 구분이 핵심입니다. **"봤다"와 "했다"를 섞으면 할 일이 사라져 사고가 납니다.**

## B-4. 상한
숫자는 **99+** 로 절단. 조직당 미처리 100건이 넘으면 뱃지가 아니라 **정리가 필요한 상태** → 소식창 상단에 안내 배너.

# C. 소식창 (알림 센터)

## C-1. 두 가지를 섞지 않는다 — 탭 2개

belie가 말한 "알림"과 "업데이트 모아보기"는 성격이 다릅니다.

| 탭 | 이름 | 내용 | 성격 |
|---|---|---|---|
| 1 | **내 알림** | 나에게 온 것 — 배정·멘션·승인 요청·처리 결과 | **행동 필요** |
| 2 | **회사 소식** | 회사에 일어난 일 — 단계 이동·새 멤버·공지·설정 변경 | **맥락 이해** |

기본 탭은 **내 알림**(할 일 우선). 벨을 누르면 패널이 열리고, "전체 보기"로 전체 페이지(`/news`)로 확장.

## C-2. 항목 구조 (한 줄로 읽히게)

```
[아이콘] [누가] [무엇을] [어디서]        [시간]
 👤      박실장이  딜 3건을 '계약' 단계로  신규업체  2시간 전
```
- **주어를 반드시 표시**(누가 했는지) — 협업의 핵심.
- 클릭 시 **해당 대상으로 바로 이동**(딥링크). 최소 클릭.
- 같은 사람이 짧은 시간에 반복한 행동은 **묶음 처리**("박실장이 딜 5건을 이동") — 피드 폭주 방지.

## C-3. 필터
`전체 / 나에게 온 것 / 딜 / 정산 / 멤버 / 공지 / 설정`. 기본 = 전체. 필터는 기억(다음 방문에 유지).

## C-4. 범위와 권한 (보안)
- **소식은 RLS를 우회하지 않는다.** 멤버(scope=assigned)는 **자기 담당 건의 소식만** 본다.
- 정산 금액 등 민감 값은 소식 문구에 **금액을 넣지 않음**("정산이 등록되었습니다" — 액수는 화면에서).
- 다른 회사의 소식은 절대 섞이지 않음(스위처 뱃지로 존재만 알림).
- **플랫폼 어드민의 break-glass 열람은 소식창에 반드시 기록**(별도 기획 §4와 연결) — 고객이 직접 확인 가능.

## C-5. 데이터 모델 (신규 · Codex가 번호 배정)

```
notifications                     -- 나에게 온 것(액션)
  id · org_id · user_id · type · title · body
  target_type · target_id · actor_id
  is_action(bool) · read_at · created_at

activity_feed                     -- 회사 소식(맥락)   ※기존 activities/audit_logs 재사용 검토
  id · org_id · actor_id · verb · target_type · target_id
  summary · created_at · group_key(묶음용)

notification_prefs
  user_id · org_id · channel(inapp|email|alimtalk) · type · enabled
```

- **기존 자산 재사용 우선**: 001의 `activities`(딜 활동)·`audit_logs`가 이미 있음. `activity_feed`를 새로 만들지, 뷰로 합칠지는 Codex 판단.
- **알림톡 연동은 Phase 2** — MVP는 인앱만(D9·D10 준수). `notification_prefs`에 자리만 만들어 둠.

## C-6. 실시간
Supabase Realtime으로 뱃지·패널 갱신. 실패 시 **60초 폴백 폴링**(조용히 열화, 오류 팝업 금지).

# G. Codex 인계 메모
- 상단바 🔔 아이콘은 **이미 존재**(Production 실측) — 자리를 새로 만들 필요 없이 내용만 연결.
- 스위처(D-S1~S5)와 같은 컴포넌트 계층에 얹는 것이 자연스러움.
- Storage 버킷 정책은 기존 계약서·서류 정책(비공개+서명URL)과 **동일 규칙** 사용.
- 마이그레이션 번호는 Codex가 최신 main 기준 배정.
