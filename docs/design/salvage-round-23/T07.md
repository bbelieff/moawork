## 3. RECOVER_NOW

### R-01. 서로 다른 ImportJob 간 경쟁과 stale preview

- **출처:** turn `019f8f84...`의 `SAFE-IMPORT-CONTRACT-01`; turn `019f8f18...`의 `PRE-01`; 현재 SPEC §5·§6·§9·§12.
- **당시 의도:** 같은 batch 재시도와 preview 이후 변경을 감지해 중복·오적용을 막는다.
- **현재 공백:** 현재 SPEC은 “같은 batch의 동시 apply”와 파일·매핑·멤버십·단계 변경은 다루지만, 서로 다른 두 batch가 같은 외부 ID나 같은 고객을 동시에 생성하는 경우와 preview 뒤 기존 데이터가 바뀌는 경우를 고정하지 않는다. `preview_hash`만으로 현재 DB의 중복 집합은 동결되지 않는다.
- **회수 가치:** apply 트랜잭션 안에서 중복·외부 ID·참조 상태를 다시 검사하고, `(workspace, source, external_id)` unique와 source-scope 단위 직렬화 또는 동등한 충돌 제어를 둔다. stale preview는 성공이 아니라 재-dry-run으로 수렴한다.
- **충돌:** Workspace 전체 lock은 작은 조직의 일반 업무 쓰기를 과도하게 막을 수 있다. lock 범위는 batch가 쓰는 source·entity·외부키로 최소화해야 한다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §5·§6·§9·§12·§16; ImportJob apply 계약; T10 cross-batch 동시성 행.
- **다음 WORK-ID:** `IMPORT-CROSS-BATCH-CONCURRENCY-01`

### R-02. Worker lease·heartbeat·fencing과 재시작

- **출처:** turn `019f8055-64b6...`의 장시간 작업·부분 반영·동시 writer 복구 경험; `round-21/08-test-matrix.md` I09와 “worker 재시작” 행.
- **당시 의도:** 작업자가 멈추거나 다시 뜰 때 이미 성공한 작업을 중복 실행하지 않고, 부분 상태를 실제 근거로 복구한다.
- **현재 공백:** 현재 import SPEC은 브라우저 종료 후 서버 ImportJob을 정본으로 삼지만 job claim owner, lease 만료, heartbeat, fencing token, 재시작 checkpoint가 없다. T08에는 테스트 기대가 있으나 이를 만족시킬 upstream 계약이 07에 없다.
- **회수 가치:** 비동기 ImportJob에는 단일 활성 claim, 짧은 lease, heartbeat, 증가하는 fencing token을 둔다. 늦게 돌아온 이전 worker는 publish·상태 전이를 거부당해야 한다. 재시작은 동일 checkpoint와 행 멱등키에서 이어진다.
- **충돌:** 작은 MVP를 하나의 짧은 DB transaction으로 끝낼 수 있다면 worker 계층은 불필요하다. 따라서 비동기 경로를 채택한 경우에만 필수 계약으로 활성화한다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §5·§11·§12·§15.1·§18.2; `ImportJob` 구현 SPEC.
- **다음 WORK-ID:** `IMPORT-JOB-FENCING-01`

### R-03. Rollback preview와 실행 사이의 CAS 재검증

- **출처:** turn `019f8f84...`의 rollback preview; turn `019f8f18...`의 `membership_version + preview_hash`; 현재 SPEC §13.
- **당시 의도:** 사용자가 import 후 수정하거나 새 업무를 연결한 행을 rollback이 파괴하지 않게 한다.
- **현재 공백:** 현재 SPEC은 rollback preview와 fingerprint 비교를 요구하지만, preview가 보인 뒤 실제 삭제 전에 다른 사용자가 수정·연결하는 경쟁조건을 다루지 않는다.
- **회수 가치:** rollback preview에도 `rollback_preview_hash`와 대상 entity version/fingerprint 집합을 고정한다. 실행 트랜잭션에서 전부 다시 비교하고 하나라도 바뀌면 삭제 0건으로 `ROLLBACK_CONFLICT`에 수렴한다.
- **충돌:** “안전 범위만 일부 rollback”은 현재 권장인 전체 batch rollback과 충돌한다. 사용자 결정 전에는 일부 rollback을 자동 허용하지 않는다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §13·§15.1·AC-12·AC-13; T10 rollback concurrency 행.
- **다음 WORK-ID:** `IMPORT-ROLLBACK-CAS-01`

### R-04. 가져온 날짜와 성과·대시보드 귀속 월 분리

- **출처:** turn `019f8a26...`의 T07 mod.perf 보류 정책; `docs/design/T07-perf-design.md` §2.1 월 귀속; 현재 `app/src/lib/dash/aggregate.ts`의 기본 `created_at` 기간 필터; `SAFE-IMPORT-CONTRACT-01`의 과거 데이터 이전 범위.
- **당시 의도:** 성과는 수납일·활동 발생일 같은 실제 업무 시각에 귀속하고, 스냅샷은 같은 입력에서 멱등 재생성한다.
- **현재 공백:** 현재 import SPEC은 정산·성과 자체는 제외하지만 고객·딜을 새로 생성한다. 이때 DB `created_at`이 import 실행 시각이면 과거 딜이 이번 달 신규 건수·리더보드·대시보드에 섞일 수 있다. “성과 데이터 제외”만으로 파생 집계 오염은 막지 못한다.
- **회수 가치:** `ingested_at`과 source business date를 분리하고, 각 지표가 사용할 귀속일을 정본으로 고정한다. source date가 없으면 과거 성과로 추론하지 않고 `date_unresolved`로 격리하거나 집계 제외한다. Import 완료 보고서는 즉시 변하는 집계를 알린다.
- **충돌:** DB `created_at`을 외부 CSV 값으로 덮어쓰면 감사·정렬 의미가 무너진다. 별도 source date 또는 기존 `applied_on` 같은 도메인 필드를 사용해야 한다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §2.2·§4.3·§16; 오늘 홈·대시보드 데이터 계약; 향후 perf import 계약.
- **다음 WORK-ID:** `IMPORT-METRIC-ATTRIBUTION-01`

### R-05. Import apply·rollback의 append-only 감사와 fail-closed

- **출처:** turn `019f8f18...`, `MEMBER-GOVERNANCE-01`의 `AUD-01/AUD-02`; 현재 import SPEC의 일반 `ImportEvent`.
- **당시 의도:** privileged 변경에 actor, reason, before/after, DB 시각을 남기고 감사 기록 실패 시 변경도 실패시킨다.
- **현재 공백:** 현재 `ImportEvent`는 이벤트 이름만 열거하며 actor role snapshot, 승인자, reason, preview hash, before/after summary, DB timestamp, denial/result, 감사 실패 처리까지 고정하지 않는다.
- **회수 가치:** apply·cancel·rollback에 append-only batch 감사 이벤트를 같은 트랜잭션 또는 원자적 publish 경계에서 기록한다. 감사에는 원본 셀이나 개인정보 대신 행 수, entity 종류, hash, 오류·중복 합계를 기록한다. 감사 저장 실패 시 publish·rollback을 성공 처리하지 않는다.
- **충돌:** 행마다 원본 before/after를 감사 원장에 복사하면 개인정보·용량이 과도해진다. 행 상세은 보호된 journal에 두고 감사는 batch 요약과 entity link hash만 가진다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §4.3·§11·§13·§14·§16; T03 감사 계약; T10 증거 manifest.
- **다음 WORK-ID:** `IMPORT-AUDIT-FAIL-CLOSED-01`

### R-06. 승인 후 권한 회수·Workspace 정지의 job cutoff

- **출처:** turn `019f8f2a...`, `AUTH-SESSION-01`의 authz epoch·Workspace 정지·멤버 비활성; 현재 import SPEC §3·§14·§15.1.
- **당시 의도:** stale 세션이나 접근 중지된 사용자가 기존 화면·토큰으로 privileged 작업을 계속하지 못하게 한다.
- **현재 공백:** 현재 SPEC은 dry-run/apply 시점의 권한 재검증은 요구하지만, 오래 실행되는 job이 승인 뒤 actor 권한 회수나 Workspace 정지를 만났을 때 publish 가능한지 고정하지 않는다.
- **회수 가치:** claim 시점과 최종 publish 직전에 Workspace status, actor membership status, import capability, authz epoch를 다시 검사한다. Workspace 정지·멤버 비활성·Owner 권한 회수는 publish를 막고 `AUTHORITY_REVOKED`로 종료한다. 단순 브라우저 종료와 보안상 권한 회수는 구분한다.
- **충돌:** “로그아웃만으로 이미 승인된 서버 작업을 취소할지”는 제품·운영 결정이다. 보안 epoch 변화는 반드시 차단하되 단순 현재기기 로그아웃은 `IMPORT-DECISION-01` 후속 질문으로 남긴다.
- **삽입 대상:** `round-21/07-safe-import-contract.md` §3·§5·§14·§15.1; T03 session/authz 계약; ImportJob 상태표.
- **다음 WORK-ID:** `IMPORT-AUTHORITY-CUTOFF-01`

### R-07. PII 없는 운영 지표와 stuck-job 경보

- **출처:** turn `019f8f18...`의 운영 경보; turn `019f8055-64b6...`의 장시간 정지·재시도 경험; 현재 import SPEC의 완료·실패 상태.
- **당시 의도:** 실패를 사용자 신고 전 발견하고, 보안·중복·복구 사고를 우선순위에 따라 운영한다.
- **현재 공백:** 현재 SPEC은 상태와 감사 이벤트는 있으나 queue 대기, parse/dry-run/apply 시간, stuck lease, 반복 retry, cross-tenant 거부, rollback conflict에 대한 비밀값 없는 운영 경보가 없다.
- **회수 가치:** 최소 지표를 `job count/state`, 단계별 duration, row count bucket, error/duplicate ratio, retry count, rollback conflict count로 제한한다. P0은 cross-tenant 쓰기 시도·권한회수 뒤 publish 시도, P1은 stuck job·반복 retry·rollback conflict 급증이다. payload에는 원본 파일명·셀·연락처를 넣지 않는다.
- **충돌:** 작은 조직 MVP에 복잡한 관제 UI를 노출하지 않는다. 사용자 화면은 진행·복구만, 운영 지표는 내부 control-plane으로 분리한다.
- **삽입 대상:** ImportJob 운영 runbook; `round-21/07-safe-import-contract.md` §15.1·§18.2; T10 운영 증거.

### E-01. 파일·행·실행시간 상한과 streaming/chunk 전환점

- **출처:** turn `019f8055-64b6...`의 장시간 작업·부분 적용 복구; `SAFE-IMPORT-CONTRACT-01`에서 제안됐으나 현재 SPEC §4.2에서 상한을 미결정으로 남긴 항목; T07 perf의 지연 재계산 부하 검토.
- **당시 의도:** 작은 조직 MVP에서 예측 가능한 시간과 메모리로 완료하면서 큰 파일 때문에 전체 서비스가 느려지지 않게 한다.
- **현재 공백:** 현재 SPEC은 CSV만 허용하지만 파일 크기, 행 수, 열 수, 한 셀 크기, dry-run/apply timeout, 동시 job 수의 운영 envelope가 없다.
- **회수 가치:** 합성 1천·1만·상한 초과 행, 넓은 CSV, 긴 셀, 오류율이 높은 파일로 streaming parser와 메모리·시간을 계측한다. 단일 transaction이 안전한 상한과 staging+atomic publish가 필요한 전환점을 정한다.
- **충돌:** 근거 없이 `10,000행/20MB` 같은 숫자를 제품 정본으로 확정하지 않는다. 작은 조직 실제 이전 분포와 실DB 부하 증거가 먼저다.
- **삽입 대상:** ImportJob 비기능 요구사항, T10 performance fixture, 사용자 업로드 제한 문구.
- **다음 WORK-ID:** `IMPORT-CAPACITY-EXPERIMENT-01`

## 12. 검증 결론

- 현재 import SPEC의 안전 기본값은 유지한다.
- 가장 큰 미회수 위험은 같은 batch가 아니라 **서로 다른 batch와 현재 DB 사이의 경쟁**이다.
- 두 번째 위험은 비동기 worker가 재시작·중복 claim·권한 회수 뒤에도 publish하는 상황이다.
- 세 번째 위험은 import 실행 시각이 source 업무 시각으로 오인되어 이번 달 대시보드·성과를 왜곡하는 것이다.
- RECOVER_NOW는 곧바로 제품 코드 구현을 뜻하지 않는다. T09가 중복 제거해 현재 SPEC 개정, VISUAL, DEV writer gate, T10 review 중 하나에 연결해야 한다.
