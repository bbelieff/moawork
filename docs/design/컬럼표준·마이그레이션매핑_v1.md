## 0. 원칙

1. **이름은 값이 정한다.** 먼데이 컬럼 제목은 참고만 하고, 실제로 무엇이 들어 있는지로 우리 컬럼을 정한다.
2. **한 칸에는 한 종류만.** 지금 먼데이는 한 칸에 두세 종류가 섞여 있다(§2). 우리는 쪼갠다.
3. **비어 있는 칸은 옮기지 않는다.** 값이 있는 칸에서 끌어온다.
4. **자동 교정은 규칙이 명확할 때만.** 애매하면 «확인 필요» 로 남기고 사람이 판정한다.

## 1. 실측 — 먼데이 신규고객 보드의 실제 값

2026-08-10 보드 조회에서 확인한 것. **컬럼 제목과 내용이 어긋나 있다.**

| 먼데이 칸 | 실제로 들어 있는 값 | 판정 |
| --- | --- | --- |
| `Name` | `도소매업` · `기타_서비스업` · `일반음식점/배달전문점` · `서비스업(음식,카페)` | **업종** |
| `회사명` | 대부분 비어 있음 | 미사용 |
| `주소` | `좋은계란` · `하늘소리` · `다산컨설팅` · `만물상회` · `냐냐샵` | **상호(회사명)** |
| `매출액` | `개인사업자` · `6,000만원_~_9,000만원` · `1,000만원_~_2,000만원` | **사업자 유형 + 매출 구간이 섞임** |
| `사업자 유형` | 비어 있음 | 미사용 |
| `대표자명` | `서영진` · `이미경` · `안정호` | ✅ 맞음 |

| `출동`(people) | `박정화` / `조은혜, 박정화` — **복수** | **협업자** |
| `담당자`(status) | 이대표 / 박정화 실장 / 담당자 미정 — **단일** | ✅ 담당자 |

**교차 증거**: 「제조업DB」 뷰의 필터가 `Name = 제조업 · OEM_위탁제조 · 자사_직접제조 …` **17가지 문자열**이다.
Name에 회사명이 들어 있었다면 이런 필터를 만들 수 없다. 「음식점DB」는 31가지.

**원인 추정**: 메타 광고 폼의 필드 순서와 보드 컬럼의 짝이 어긋난 채로 오래 쌓였다.
→ **원천(광고 폼 매핑)을 먼저 고쳐야 앞으로 들어올 건이 깨끗해진다.**

## 2-2. 날짜 칸은 전부 달력이다

**손으로 «08-11» 을 타이핑하면 형식이 사람마다 갈라진다.** `8/11` · `08.11` · `8-11` 이 한 칸에 섞이면 정렬도 필터도 무너진다. 그래서 «사람이 넣는 날짜 칸»(✎ 입력)은 예외 없이 달력에서 고른다. ⟳ 수집·ƒ 수식 날짜는 애초에 사람이 못 건드린다.

달력이 붙는 칸 — 총 11개

| 탭 | 칸 |
| --- | --- |
| 신규리드 | 재통화 일시 · 대면미팅 일시 · **재접촉일** |
| 리드컨택 | 전자계약 / 미팅일정 · **재접촉일** |
| 계약업체 실무 | 방문 및 신청 일 · 실사일 · **예상 심사 종료** · 수수료_입금일 · **조달일** · 계약금_입금일 |

> **창업년도는 날짜가 아니다.** 값이 `2019` · `2012` 처럼 연도 하나뿐이라 달력을 띄우면 오히려 방해가 된다. 숫자 칸으로 둔다.

## 2-3. 계약업체 실무 — 날짜에서 날짜가 나온다

녹취 실측: *"조달 날짜는 고객이 조달된 날짜로 설정… 거기에 따라서 D-day 365일이 생겨지게 되고"*

**재신청 안내일을 손으로 적지 않는다.** 조달일만 넣으면 나온다.

| 칸 | 출처 | 규칙 |
| --- | --- | --- |
| **조달일** | ✎ 입력 | 고객이 실제로 자금을 받은 날. 달력 |
| ƒ재신청 안내일 | ƒ 수식 | **조달일 + 365** — 1년 뒤 다시 신청할 수 있다 (D67) |
| ƒD+180 | ƒ 수식 | 조달일 + 180 — 중간 점검 |
| **예상 심사 종료** | ✎ 입력 | 녹취: *"7월 6일부터 한 달 반"*. 기관·상품마다 다르므로 사람이 넣는다 |
| ƒ심사 D-day | ƒ 수식 | 예상 심사 종료 − 오늘. 다가오면 확인 |

> 먼데이는 `재신청 안내일` 이 **손입력**이었다. 조달일이 바뀌면 재신청일이 따라 바뀌지 않아, 1년 뒤 재접촉 기회를 통째로 놓친다. 이 한 줄이 §6 D67 의 실체다.

## 3. 마이그레이션 매핑 — 기본값

### 3-1. 단순 이동

| 먼데이 | → 우리 | 규칙 |
| --- | --- | --- |
| `주소` | **회사명** | 값이 있으면 그대로 |
| `Name` | **업종** | 17·31가지 문자열 → 8종 업종으로 정규화(§3-3) |
| `대표자명` | 대표자명 | 그대로 |
| `연락처` | 연락처 | 숫자만 추출 |
| `출동` | **협업자** | 복수 그대로 |
| `담당자` | 담당자 | 라벨 id 보존 |
| `상담 상황` | 상담 상황 | **라벨 id 보존**(순번 아님) |
| `📬…` 5종 | 안내 문자 5종 | 접두어 제거 |

### 3-2. 한 칸 → 두 칸 (분해)

`매출액` 칸의 값을 **패턴으로 판정**한다.

```
값이 금액 구간 형태     ( 숫자 + 만원|억 + ~ )   → 매출 구간
값이 사업자 유형 목록에 있음 (개인사업자·법인·개인/간이…) → 사업자 유형
둘 다 아님                                        → 확인 필요
```

### 3-3. 업종 정규화

Name에 들어 있던 17·31가지 표기를 8종으로 접는다. 예:

```
제조업 · OEM_위탁제조 · 자사_직접제조 · ODM제조업 · 개인사업자_제조업 …   → 제조업
일반음식점 · 배달전문점 · 카페_/_음식점업 · 음식점&카페 …                  → 일반음식점/배달전문
```

**원문은 버리지 않는다.** `원본_업종표기` 라는 보조 필드에 남겨 되돌릴 수 있게 한다.

### 3-4. 회사명이 비는 경우

`주소`도 비어 있으면 회사명을 만들 수 없다.
→ **«회사명 없음»으로 표시하고 마스터에 등록하지 않는다.** 리드로만 남긴다(리드는 회사가 아니다).

## 4. 착수 전 반드시 할 것 — 분포 조사

교정 규칙을 확정하려면 **8,400건이 얼마나 규칙적으로 어긋나 있는지**를 먼저 세어야 한다.

| 세어야 할 것 | 왜 |
| --- | --- |
| `주소`가 비어 있는 건수 | 회사명을 못 만드는 건수 = 마스터 등록 불가 |
| `매출액`이 금액 패턴인 건수 / 사업자유형 패턴인 건수 / 그 외 | 분해 규칙이 몇 %를 덮는지 |
| `Name`이 업종 목록에 없는 값인 건수 | 정규화 예외 |
| `회사명`에 값이 있는 건수 | 있으면 그쪽이 우선 |

**읽기 전용 조회로 건수만 뽑는다. 고객 데이터 내용은 기록하지 않는다.**

## 5. 되돌릴 수 있게

- 모든 이동에 `원본_컬럼` · `원본_값` 을 보조 테이블에 남긴다
- 「확인 필요」로 분류된 건은 **자동 교정하지 않고** 목록으로 남긴다
- 마이그레이션은 **미리보기 → 건수 대조 → 실행** 3단계. 미리보기 없이 실행 금지
