## 1. 해결할 문제와 1~10명 조직의 사용자 가치

작은 조직은 대표 혼자 시작해 첫 사원을 초대하고, 일이 늘면 팀장을 세우며, 실제 필요가 생겼을 때 두 번째 팀을 연다. 처음부터 복잡한 조직도·직급표·세부 ACL을 요구하면 대표는 업무를 시작하기 전에 관리자가 되어야 한다.

`우리 팀 키우기`가 해결할 핵심 문제는 다음과 같다.

- 대표가 안전하게 팀장·사원을 초대한다.
- 초대 상태를 이해하고 만료·취소·재전송을 복구한다.
- 새 멤버가 수락한 뒤 실제 첫 업무를 배정한다.
- 휴직·퇴사 시 접근을 먼저 차단하고 기존 업무를 잃지 않고 넘긴다.
- 두 번째 팀이 필요해진 순간에만 팀 기능을 발견한다.
- 팀 구조를 바꿔도 데이터 접근권한이 조용히 바뀌지 않는다.

작은 조직의 기본 가치 흐름은 다음과 같다.

```text
대표 혼자 시작
  → 첫 사원 초대
  → 수락 후 첫 업무 배정
  → 필요할 때 팀장 지정
  → 성장 신호가 생기면 두 번째 팀 제안
  → 휴직·퇴사 시 접근 중지 후 업무 인계
```

## 2. 결정 상태

### 2.1 확정 결정

- 초기 기본 조직은 `대표(보호된 Owner) → 팀장 → 사원`이다.
- 마지막 Owner 보호, tenant/RLS 격리, 최소권한, 세션 회수, 감사는 화면에서 숨겨져도 항상 적용한다.
- 복잡 조직도, C-level, 사용자 정의 계층, 세밀한 ACL과 고급 감사는 기본 경험에 노출하지 않는다.
- 초대 상태는 안전하게 관리하며 재전송 시 이전 링크를 무효화한다.
- 첫 업무의 기본 시퀀스는 `초대 → 수락 → 첫 업무 배정`이다.
- 휴직·퇴사는 접근 차단을 먼저 수행하고 업무 인계를 별도 작업으로 처리한다.
- 업무 인계 필요 여부를 멤버 lifecycle 상태와 혼합하지 않는다.
- 팀 생성·팀 이동만으로 업무 데이터 ACL을 자동 변경하지 않는다.
- 두 번째 팀을 자동 생성하거나 사람을 자동 이동하지 않는다.
- 대량 초대, 복잡 권한표, 고급 감사 화면은 1~10명 기본 범위에서 제외한다.

| D2 | 팀장 표시는 가능하되 실제 업무 배정 권한은 별도 결정·위임으로 연다. | 직급과 capability를 분리한다. |

### 2.3 미결정 — 사용자 역인터뷰

#### Q1. 초대 정책

기본 만료기간, 재전송 대기시간, 대표 외 팀장의 초대 허용 여부를 정해야 한다.

**추천:** 초기에는 대표만 초대하고, 재전송은 짧은 cooldown 뒤 허용하며 새 링크가 만들어지면 이전 링크를 즉시 무효화한다.

#### Q2. 팀장 권한

팀장 지정만으로 자기 팀 업무 배정 권한을 줄지, 대표가 별도로 위임할지 정해야 한다.

**추천:** 팀장 표시는 즉시 가능하되 업무 배정 권한은 대표가 명시적으로 위임한다.

#### Q3. 두 번째 팀 공개 신호

인원수, 한 사람의 직속 인원, 반복되는 업무 배정 부담, 사용자의 수동 선택 중 무엇을 기준으로 제안을 보여줄지 정해야 한다.

**추천:** 사용자의 `팀 나누기` 선택과 반복되는 운영 부담을 우선 신호로 삼고, 인원수는 보조 신호로만 사용한다.

## 3. Progressive disclosure — 대표→팀장→사원

`1→3→10`은 고정 인원수 규칙이 아니라 작은 조직이 성장하면서 화면을 여는 대표 시나리오다.

| 성장 단계 | 기본 노출 | 이 단계에서 하는 일 | 계속 숨길 것 |
|---|---|---|---|
| 대표 1명 | 현재 회사, 대표 역할, 내 정보, 로그인 기기, 로그아웃, `첫 직원 초대` | 첫 사원 초대 | 팀 관리, 조직도, 권한표, 감사 |
| 대표+팀장+사원 | 멤버 목록, 역할 표시, 초대 대기·만료·취소·재전송, 수락 후 첫 업무 배정 | 일상적인 초대·배정·접근 중지 | 세밀한 capability, 복수 팀, 사용자 정의 계층 |
| 여러 사람이 함께 일하는 단계 | `팀 나누기` 발견 경로, 팀장·구성원 선택, 이동 영향 미리보기 | 두 번째 팀을 사용자 확인 뒤 생성 | C-level, 자동 ACL, 다단계 계층, 고급 감사 |

### 역할별 기본 경험

| 역할 | 바로 보이는 것 | 기본 행동 | 금지선 |
|---|---|---|---|
| 대표 | 전체 멤버, 초대 상태, 접근 중지·인계 필요 | 초대, 역할 표시, 첫 업무 배정, 접근 중지 | 자기 자신을 마지막 Owner 상태에서 중지·퇴사 처리 |
| 팀장 | 자기 팀 구성원과 위임받은 업무 범위 | 위임된 범위 안의 업무 배정 | Owner 관리, tenant 전체 권한, 자동 ACL 변경 |
| 사원 | 현재 회사·팀·역할, 내게 배정된 업무 | 초대 수락, 내 업무 수행 | 멤버 관리, 타 팀 데이터 접근 |

팀장은 직급 이름만으로 capability를 얻지 않는다. Q2 결정 전에는 `팀장 표시`와 `팀 업무 배정 권한`을 분리한다.

## 4. 초대 계약

### 4.1 초대 상태

| 내부 상태 | 기본 사용자 표시 | 허용 행동 | 전이·제약 |
|---|---|---|---|
| `invite_draft` | 작성 중 또는 미표시 | 발송·삭제 | membership 없음, 토큰 없음 |
| `invite_pending` | 초대 대기 | 재전송·취소 | 정확한 인증 계정만 수락 가능 |
| `invite_expired` | 초대 만료 | 다시 초대 | 이전 링크 사용 불가 |
| `invite_cancelled` | 초대 취소 | 새 초대 | 모든 기존 링크 사용 불가 |
| `invite_accepted` | 근무 중으로 전환 | 첫 업무 배정 | membership은 한 번만 생성 |

`delivery_failed`는 초대 lifecycle이 아니라 전달 결과다. 알림 발송에 실패해도 안전한 `invite_pending` 기록을 삭제하지 않는다.

### 4.2 초대 기본 시퀀스

```text
초대 작성
  → tenant 안의 활성 멤버·대기 초대 중복 확인
  → invite_pending 생성
  → 일회용 링크와 만료시각 생성
  → 알림 전달 시도
  → 정확한 인증 계정·미사용·미만료 확인
  → 최소권한 membership 생성
  → 링크 소비
  → 대표에게 첫 업무 배정 CTA
```

### 4.3 취소·만료·재전송

- 취소는 즉시 기존 링크를 사용할 수 없게 만든다.
- 만료 링크는 membership을 만들지 않는다.
- 재전송은 중복 초대를 새로 만들지 않고 새 링크·만료시각·발송 회차로 갱신한다.
- 재전송 이후 이전 링크는 거부한다.
- 전달 실패 원인은 필요한 범위에서만 안내하고 내부 토큰이나 비밀값을 노출하지 않는다.
- 잘못된 대상이 이미 수락했다면 계정을 바꿔 끼우지 않는다. 잘못 생성된 멤버십을 안전하게 중지하고 올바른 대상을 다시 초대한다.

## 5. 초대 수락과 첫 업무 배정

### 5.1 확정 기본 시퀀스

초대 전에 업무를 `pending_assignment`로 예약하는 흐름은 기본 범위에서 제거한다.

```text
초대 발송
  → 수락 대기
  → membership 활성화
  → 대표의 멤버 화면에 "첫 업무를 배정해 주세요"
  → 대표가 기존 업무 또는 새 업무 선택
  → 신규 멤버의 오늘 화면에 첫 업무 표시
```

### 5.2 화면 계약

- 대기 중인 초대에는 `첫 업무 배정 완료`처럼 보이는 상태를 표시하지 않는다.
- 수락한 멤버에게 현재 회사, 팀, 역할, 첫 배정 업무를 한 화면에서 알려준다.
- 대표가 첫 업무를 아직 배정하지 않았으면 신규 멤버의 빈 상태에는 `아직 배정된 업무가 없어요`와 안전한 다음 행동을 표시한다.
- 팀장·사원은 Owner용 회사 설정이나 고급 권한 화면으로 보내지 않는다.

### 5.3 데이터 계약

- 첫 업무는 존재하는 active membership에만 배정한다.
- 초대 수락과 업무 배정은 서로 다른 작업 단위다.
- 업무 배정 실패가 membership 수락을 되돌리지 않는다.
- 재시도는 업무 중복 생성·중복 배정을 만들지 않는다.
- 초대 취소·만료 상태에는 기본 흐름에서 예약 업무를 연결하지 않는다.

## 6. 휴직·퇴사와 업무 인계

### 6.1 기본 사용자 상태

| 상태 | 기본 표시 | 접근 | 복구 |
|---|---|---|---|
| `member_active` | 근무 중 | 현재 역할·범위 안에서 허용 | 해당 없음 |
| `access_suspended` | 휴직·접근 중지 | 모든 기존 세션 폐기, 새 접근 거부 | 복귀 시 최소권한부터 재승인 |
| `offboarded` | 퇴사 | 접근 불가 | 직접 복구하지 않고 새 초대 |

`leave_scheduled` 같은 예약·정책 상세는 기본 화면에서 숨긴다. 필요해질 때 고급 흐름으로 연다.

### 6.2 접근 중지 시퀀스

```text
대상과 Owner 불변식 확인
  → 접근 중지 의도 확인
  → 기존 로그인 세션·refresh 권한 폐기
  → 새 요청 deny
  → 업무 인계 필요 목록 생성
  → 성공한 업무만 새 담당자에게 재배정
  → 실패 항목은 미배정·재시도 큐에 유지
  → 접근 중지와 인계 결과 기록
```

- 마지막 Owner는 후임 Owner가 안전하게 확정되기 전 중지·퇴사 처리할 수 없다.
- 알림 실패는 접근 차단이나 성공한 업무 인계를 롤백하지 않는다.
- 브라우저와 모바일을 포함한 기존 세션을 함께 무효화한다.
- 휴직 복귀는 최소권한부터 시작하며 과거 팀장 위임을 자동 복원하지 않는다(Draft).
- 퇴사자는 새 초대를 통해서만 재입사한다.

### 6.3 업무 인계는 별도 작업 큐

`handoff_required`를 멤버 상태로 사용하지 않는다. 멤버 접근상태와 업무 인계 진행상태를 분리한다.

| 인계 상태 | 의미 | 허용 행동 |
|---|---|---|
| `handoff_required` | 넘겨야 할 업무가 있음 | 인계자 선택·미배정 유지 |
| `handoff_in_progress` | 일부 업무를 옮기는 중 | 실패 항목 재시도 |
| `handoff_completed` | 모든 대상 업무 처리됨 | 결과 확인 |

업무는 삭제하지 않는다. 인계 실패 항목은 명시적인 미배정 큐에 남기고 조용히 누락하지 않는다.

## 7. 두 번째 팀과 성장 신호

### 7.1 공개 원칙

- `7명 이상`, `직속 5명 이상` 같은 숫자는 확정 규칙이 아니다.
- 숫자는 후보 신호일 뿐이며 실제 트리거는 `TEAM-GROWTH-DECISION-01`에서 결정한다.
- 제안은 차단 없는 배너나 설정의 발견 경로로 제공한다.
- 팀을 자동 생성하거나 멤버를 자동 이동하지 않는다.

### 7.2 추천 Draft 신호

- 대표·팀장이 반복해서 같은 구성원 묶음에 업무를 배정한다.
- 한 사람이 관리하는 구성원이 늘어 배정·검토 누락이 반복된다.
- 사용자가 직접 `팀 나누기`를 선택한다.
- 인원수는 보조 신호로 사용하되 숫자 하나로 자동 실행하지 않는다.

### 7.3 팀 나누기 흐름

```text
두 번째 팀이 필요해졌나요?
  → 새 팀 이름
  → 팀장 후보 선택
  → 구성원 선택
  → 기존 업무 배정 유지·변경 영향 미리보기
  → 권한은 바뀌지 않음을 설명
  → 사용자 확인
  → 팀·구성원 관계만 적용
```

### 7.4 고급 ACL 금지선

첫 버전의 팀 분리는 명단, 알림, 업무 배정 편의를 제공한다. 다음은 기본 범위에 넣지 않는다.

- 팀 생성에 따른 데이터 접근 자동 축소·확대
- 필드·보드·고객별 사용자 정의 권한
- 다단계 상속 ACL
- C-level과 사용자 정의 직급 체계
- 팀 간 예외 권한 매트릭스
- 팀장 이름만으로 tenant 전체 관리 capability 부여

팀별 데이터 ACL이 실제로 필요해지면 별도 역인터뷰·권한 계약·RLS 검수를 거친다.

## 8. 화면·파일·데이터·상태 계약

### 8.1 화면 계약

- 1명 조직은 `첫 직원 초대` 하나를 주 행동으로 본다.
- 3명 조직은 대표·팀장·사원과 초대·첫 배정 상태를 한눈에 본다.
- 성장한 조직은 기존 일상을 막지 않는 `팀 나누기` 제안을 본다.
- 초대·접근 중지·인계 오류는 `무슨 일 → 현재 상태 → 다음 행동` 순으로 설명한다.
- 파괴적 행동 전 영향 대상과 되돌릴 수 있는 범위를 알려준다.

### 8.2 파일 계약

- 이 작업은 `docs/design/round-21/06-small-team-growth.md` 하나만 소유한다.
- `01-first-value-concepts.md`, `INDEX.md`, coordination, worklog, 코드, HTML, DB를 수정하지 않는다.
- T04 시각 산출물과 DEV 구현은 사용자 결정과 별도 file lease 뒤에만 시작한다.

### 8.3 데이터 계약

- 초대, membership, 팀, 업무 인계는 tenant 식별자를 갖고 서로 다른 tenant를 참조할 수 없다.
- 초대 수락은 단일 membership만 만든다.
- 팀 관계와 데이터 접근권한은 별도 계약이다.
- 접근 차단과 session revoke는 알림 전달 성공 여부와 분리한다.
- 인계는 성공 항목만 반영하고 실패 항목을 재시도 가능하게 남긴다.

### 8.4 상태 계약

- 사용자 표시 상태와 내부 처리 상태를 분리한다.
- `invite_draft`, 토큰 소비, 전달 실패 상세는 필요한 순간에만 보여준다.
- 멤버 접근 상태와 업무 인계 상태를 혼합하지 않는다.
- 미확정 팀장 권한과 두 번째 팀 숫자 트리거를 제품 규칙처럼 저장하지 않는다.

## 10. 테스트와 수용조건

### 10.1 초대

- [ ] draft 상태에는 membership과 수락 링크가 없다.
- [ ] pending 초대는 정확한 인증 계정에서 한 번만 수락된다.
- [ ] 만료·취소·재전송 이전 링크는 수락이 거부된다.
- [ ] 재전송해도 초대와 membership이 중복되지 않는다.
- [ ] 활성 멤버와 대기 초대 중복을 감지한다.
- [ ] 전달 실패가 pending 초대를 삭제하지 않는다.
- [ ] 다른 tenant의 초대·membership을 조회하거나 수락할 수 없다.

### 10.2 첫 업무

- [ ] 수락 전에는 기본 흐름에서 업무를 예약·배정하지 않는다.
- [ ] 수락 뒤 대표에게 첫 업무 배정 CTA가 나타난다.
- [ ] 업무 배정 실패가 active membership을 되돌리지 않는다.
- [ ] 재시도해도 업무가 중복 생성·배정되지 않는다.
- [ ] 신규 멤버가 현재 회사·팀·역할·첫 업무를 10초 안에 이해한다.

### 10.3 휴직·퇴사·인계

- [ ] 마지막 Owner의 접근 중지·퇴사가 차단된다.
- [ ] 휴직·퇴사 처리 즉시 모든 기존 세션이 무효화된다.
- [ ] 알림 실패 뒤에도 접근 차단은 유지된다.
- [ ] 담당 업무는 삭제되지 않고 인계 큐에 남는다.
- [ ] 인계 일부 실패 시 성공 항목은 유지하고 실패 항목만 재시도한다.
- [ ] 휴직 복귀 시 과거 고권한이 자동 복원되지 않는다(Draft 결정 반영 후).

### 10.4 두 번째 팀

- [ ] 인원수만으로 팀을 자동 생성하거나 멤버를 이동하지 않는다.
- [ ] 적용 전 팀장·구성원·기존 업무 영향을 미리 보여준다.
- [ ] 팀 생성·이동 전후 업무 데이터 ACL이 자동으로 변하지 않는다.
- [ ] 팀장 capability는 Q2 결정과 명시적 위임을 따른다.

### 10.5 시각·접근성

- [ ] 모바일에서 초대 상태, 재전송, 취소, 접근 중지, 인계 CTA를 구분한다.
- [ ] 상태를 색상만으로 전달하지 않는다.
- [ ] 키보드로 초대·취소·재전송·인계 흐름을 수행한다.
- [ ] 오류가 발생한 항목으로 포커스가 이동하고 다음 행동을 읽을 수 있다.
- [ ] 고급 ACL·Platform 기능이 기본 화면의 주인공으로 나타나지 않는다.
