## 1. 해결할 문제와 작은 조직의 가치

초기 고객은 대표·팀장·사원으로 시작하는 작은 조직이다. 첫 로그인 뒤 조직도, 세부 권한, 플랫폼 관리부터 설정하게 하면 사용자는 실제 업무 가치를 보기 전에 이탈한다.

`3분 시작`은 다음 한 줄을 완주시키는 첫 가치 흐름이다.

```text
로그인 → 보호된 Owner와 회사 생성 → 선택적 팀원 초대 → 첫 고객·첫 업무 → 오늘 화면
```

사용자 가치는 다음과 같다.

- 대표 혼자라도 회사 이름과 첫 고객만으로 즉시 시작한다.
- 팀과 시작할 때는 사원·팀장 두 역할만 선택한다.
- 첫 고객을 만들면 다음에 할 첫 업무까지 이어진다.
- 중간에 그만두거나 저장이 실패해도 처음부터 다시 하지 않는다.
- 고급 관리 기능은 숨기되 Owner 보호와 tenant 격리는 항상 적용한다.

### 전체 → 부분 → 전체

- **전체 의도:** 교육 없이 3분 안에 실제 업무가 있는 오늘 화면에 도착한다.
- **부분 설계:** 회사, 팀, 첫 고객·업무를 네 가지 서로 다른 진행 구조로 비교한다.
- **전체 재검증:** 어느 안도 작은 조직의 시작을 고급 관리자 설정으로 바꾸거나, 단순함을 이유로 보안·복구 계약을 약화해서는 안 된다.

## 2. 결정 상태

### 2.1 확정 결정

- 초기 기본 조직은 `대표(보호된 Owner) → 팀장 → 사원`이다.
- 회사 생성자는 정확히 한 명의 보호된 Owner로 시작한다.
- C-level, 사용자 정의 계층, 세부 ACL, Platform 운영은 기본 시작 화면에서 숨긴다.
- 팀장·사원으로 초대된 회원에게 Owner용 회사 생성 흐름을 노출하지 않는다.
- 예시에는 실제 고객정보, 개인정보, 비밀값을 사용하지 않는다.
- 제품 코드·DB 구현은 사용자 역인터뷰, 4안 시각 비교, T10 검수와 사용자 승인 뒤에만 시작한다.

### 2.2 권장 Draft 기본값

아래는 사용자가 아직 확정하지 않은 권장안이다. T04는 결정처럼 고정하지 말고 시안에서 분기 가능하게 표현한다.

| ID | 권장 Draft | 이유 |
|---|---|---|
| D1 | 혼자 시작을 기본으로 하고 팀 초대는 선택한다. | 1인 대표가 추가 설정 없이 시작할 수 있다. |
| D2 | 초대 역할은 `사원` 기본, `팀장` 선택으로 제한한다. | 작은 조직에 필요한 최소 역할만 보여준다. |
| D3 | 고객 이름만 필수로 받고 `첫 연락하기·오늘·현재 사용자 담당` 업무를 자동 제안한다. | 첫 고객 등록을 실제 다음 행동으로 연결한다. |
| D4 | 예시는 화면에만 표시하고 tenant 데이터로 저장하지 않는다. | 가짜 고객 삭제와 실제 데이터 혼동을 없앤다. |
| D5 | 회사·Owner 생성만 필수이며 초대와 첫 고객은 건너뛰고 오늘 화면에서 재개할 수 있다. | 온보딩에 갇히지 않으면서 시작을 다시 찾을 수 있다. |

### 2.3 사용자 미결정 Q1~Q5

| 질문 | 권장 기본값 | 답에 따라 바뀌는 것 |
|---|---|---|
| Q1. 혼자/팀 시작을 별도 단계로 나눌까? | 혼자 기본 + 선택적 초대 | 화면 수, 분기 위치, A/B/C/D 적합도 |
| Q2. 초대 시 역할을 선택할까? | 사원 기본 + 팀장 선택 | 초대 카드, 역할 저장, 첫 방문 설명 |
| Q3. 첫 고객과 첫 업무를 함께 만들까? | 하나의 원자적 행동으로 생성 | 필수 입력, 성공 기준, 실패 복구 |
| Q4. 예시 데이터를 실제로 저장할까? | 화면 예시만 표시 | 빈 상태, 삭제 UX, 데이터 격리 |
| Q5. 첫 고객 전에도 오늘 화면에 갈 수 있을까? | 가능, 재개 카드 제공 | 완료 조건, 건너뛰기, 재개 위치 |

## 3. 공통 계약

### 3.1 화면 계약

네 안 모두 다음을 10초 안에 알 수 있어야 한다.

- 지금 만드는 회사가 어디인지
- 내 역할이 보호된 대표인지
- 지금 해야 할 한 가지 행동이 무엇인지
- 선택 항목을 건너뛸 수 있는지
- 실패했을 때 무엇이 보존됐고 무엇을 다시 해야 하는지

초대받은 팀장·사원의 첫 방문은 별도 축약 흐름이다.

```text
현재 회사 확인 → 내 역할·팀 확인 → 첫 배정 업무 → 역할별 오늘 화면
```

회사 생성, Owner 변경, 전체 조직 설정은 보여주지 않는다.

### 3.2 파일 계약

- 이 SPEC의 소유 파일은 `docs/design/round-21/01-first-value-concepts.md` 하나다.
- 사용자 결정 전에는 제품 코드, DB, migration, HTML을 만들지 않는다.
- T04 시각 산출물은 MWC가 `FIRST-VALUE-DECISION-01`을 닫고 별도 file lease를 발급한 뒤 작성한다.
- 기존 T04 관리자·계정 HTML, T10 검수 문서, T09 `INDEX.md`를 이 작업에서 수정하지 않는다.
- 이 SPEC의 Draft와 확정값이 바뀌면 T09가 허브에서 downstream 상태를 갱신하며, T01이 다른 writer 파일을 대신 수정하지 않는다.

### 3.3 데이터·권한 계약

- `Workspace+Owner membership`은 함께 성공하거나 함께 실패한다.
- `첫 고객+첫 업무`는 함께 성공하거나 함께 실패한다.
- 초대는 Workspace 생성 뒤 별도 작업 단위로 처리한다. 초대 실패가 안전하게 생성된 Workspace를 되돌리지 않는다.
- 모든 쓰기의 tenant 문맥은 클라이언트 입력이 아니라 인증된 서버 문맥으로 확정한다.
- Owner 이전·강등·삭제는 시작 흐름에서 제공하지 않는다.
- 사원은 최소권한 프리셋, 팀장은 팀 범위 프리셋을 사용한다. 세부 ACL은 고급 설정으로 미룬다.
- 동일 요청 재시도, 뒤로 가기, 새로고침, 재개가 중복 Workspace·초대·고객·업무를 만들지 않아야 한다.
- 진행 상태에는 단계 식별자와 완료 여부만 보존하고 작성 중 개인정보를 불필요하게 장기 저장하지 않는다.

### 3.4 공통 상태

| 상태 | 사용자에게 보여줄 것 | 계약 |
|---|---|---|
| 첫 진입 | 3분 시작의 목적과 첫 행동 | 고급 설정 비노출 |
| 입력 중 | 필수·선택 구분, 다음 결과 | tenant 미생성 상태를 성공처럼 표시하지 않음 |
| 저장 중 | 중복 제출 방지, 진행 표시 | 동일 요청 멱등 처리 |
| 부분 완료 | 완료 항목과 남은 항목 | 성공한 작업을 실패로 되돌리지 않음 |
| 전체 완료 | 현재 회사·역할·첫 업무와 오늘 화면 CTA | 실제 저장 결과와 일치 |
| 건너뜀 | 무엇을 미뤘는지와 재개 위치 | 필수 계약은 건너뛰지 않음 |
| 재방문 | 마지막 완료 지점과 안전한 다음 행동 | 다른 Workspace의 진행 상태 비노출 |
| 권한 없음 | 현재 역할과 가능한 다음 행동 | 권한 상승·Owner 우회 금지 |

## 4. 콘셉트 A — 한 장 빠른 시작

### 구조 축

`단일 화면 / 세로 카드 / 카드별 즉시 저장 / 인라인 복구`

```text
┌─────────────────────────────────────┐
│ MoaWork 3분 시작                    │
│ 회사와 첫 업무만 만들면 시작돼요    │
├─────────────────────────────────────┤
│ ① 회사                              │
│ [회사 이름________________] [저장됨] │
├─────────────────────────────────────┤
│ ② 팀원도 초대할까요?       [선택]   │
│ [초대 대상________] [사원▼] [+추가] │
│ [지금은 혼자 시작할게요]             │
├─────────────────────────────────────┤
│ ③ 첫 고객                           │
│ [고객 이름________________]          │
│ 첫 업무 [첫 연락하기____] [오늘▼]   │
├─────────────────────────────────────┤
│ [오늘의 MoaWork 시작하기]            │
└─────────────────────────────────────┘
```

### 진행·재개

- 화면 수는 시작 1면과 오늘 화면이다.
- 위에서 아래로 진행하되 완료 순서는 유연하다.
- 초대와 첫 고객 카드는 각각 건너뛸 수 있다(Draft).
- 오늘 화면에는 완료하지 않은 카드만 재개 항목으로 남긴다.

### 실패·복구

- 실패는 해당 카드 안에 표시하고 다른 성공 카드는 유지한다.
- 회사 생성 실패 시 팀·고객 저장을 시작하지 않는다.
- 첫 고객·업무 실패 시 입력을 유지하고 두 항목을 함께 재시도한다.
- 초대 일부 실패 시 성공·실패 대상을 분리하되 민감한 상세 원인은 노출하지 않는다.

### 장점·위험

- 장점: 가장 짧고 전체 흐름이 한눈에 보인다.
- 위험: 모바일에서 초대 행과 선택 입력이 늘면 정보 밀도가 높아진다.
- 숨은 계약 위험: 카드별 저장 경계가 사용자에게 하나의 저장처럼 오해될 수 있다.

### A안 수용조건

- 모바일에서 기본 경로가 과도한 스크롤 없이 3분 안에 완료된다.
- 성공·선택·미완료 카드가 시각적으로 구분된다.
- 부분 실패 뒤 성공 카드가 중복 저장되지 않는다.

## 5. 콘셉트 B — 하나씩 묻는 3단계 가이드

### 구조 축

`다중 화면 / 한 화면 한 질문 / 선형 체크포인트 / 단계 단위 복구`

```text
[1/3 회사]
회사 이름은 무엇인가요?
[________________]                         [다음]

[2/3 팀]
지금 누구와 시작하나요?
(●) 혼자 시작
( ) 팀원과 시작  [초대 대상] [사원/팀장]
[이전]                                      [다음]

[3/3 첫 고객]
[고객 이름________]
[✓ 첫 연락하기 업무도 만들기]
[나중에 하기]                              [완료]

[성공]
첫 업무가 준비됐어요.              [오늘 화면으로]
```

### 진행·재개

- 질문 3면과 성공 1면으로 구성한다.
- 한 단계씩 진행하며 뒤로 가도 완료된 서버 작업을 중복 실행하지 않는다.
- 2·3단계는 건너뛸 수 있다(Draft).
- 마지막 안전 체크포인트에서 재개한다.

### 실패·복구

- 오류가 난 현재 단계에 머물고 입력을 보존한다.
- 이전 단계로 돌아가 회사 이름을 바꿀 때 이미 생성된 Workspace를 새로 만들지 않고 허용된 이름 변경으로 다룬다.
- 초대 실패와 고객·업무 실패는 서로 다른 단계에서 격리한다.

### 장점·위험

- 장점: 한 번에 한 질문이라 교육 없이 가장 이해하기 쉽고 접근성 구조가 명확하다.
- 위험: 혼자 시작하는 숙련 사용자에게 단계가 길게 느껴질 수 있다.
- 숨은 계약 위험: 뒤로 가기와 재개가 생성 API를 다시 호출하면 중복 데이터가 생길 수 있다.

### B안 수용조건

- 단계 제목, 현재 위치, 이전·다음 결과를 보조기술이 이해할 수 있다.
- 새로고침 후 마지막 완료 단계로 정확히 복귀한다.
- 뒤로 가기 후 다시 진행해도 생성 건수가 늘지 않는다.

## 6. 콘셉트 C — 오늘 홈부터 보여주기

### 구조 축

`회사만 필수 / 실제 제품에 즉시 진입 / 비선형 시작 과업 / 복구 카드`

```text
[필수 1면]
회사 이름을 알려주세요.
[________________] [회사 만들고 시작하기]

                 ↓

┌ 오늘의 MoaWork ─────────────────────┐
│ 현재 회사 · 내 역할: 대표            │
│                                     │
│ 시작할 준비를 마쳐볼까요?      1/3 │
│ [✓] 회사 만들기                     │
│ [ ] 첫 고객과 업무 만들기   [시작] │
│ [ ] 팀원 초대하기           [시작] │
│                    [오늘은 접어둘게요]│
├─────────────────────────────────────┤
│ 오늘 할 일                          │
│ 아직 업무가 없어요. [첫 업무 만들기]│
└─────────────────────────────────────┘
```

### 진행·재개

- 회사 생성 1면 뒤 바로 실제 오늘 화면에 진입한다.
- 첫 고객·업무와 팀 초대는 사용자가 원하는 순서로 진행한다.
- 시작 카드는 접거나 나중으로 미룰 수 있다(Draft).
- 오늘 화면과 설정의 `시작 가이드`에서 언제든 재개한다.

### 실패·복구

- 실패한 항목은 홈에서 `다시 시도 필요` 카드로 바뀐다.
- 카드에는 발생한 일, 보존된 결과, 다음 행동을 표시한다.
- Workspace가 생성되지 않은 상태에서는 실제 홈으로 보내지 않는다.

### 장점·위험

- 장점: 온보딩에 갇히지 않고 실제 제품과 일상 화면을 가장 빨리 경험한다.
- 위험: 빈 홈에서 첫 고객 등록을 계속 미룰 수 있다.
- 숨은 계약 위험: 미완료 상태를 정상 완료로 간주하면 업무·초대 전제조건이 조용히 빠질 수 있다.

### C안 수용조건

- 빈 홈에서도 사용자가 다음 행동을 10초 안에 찾는다.
- 시작 카드를 접은 뒤에도 재개 경로를 다시 찾을 수 있다.
- 팀장·사원은 Owner 체크리스트가 아니라 각자의 첫 배정 업무를 본다.

## 7. 콘셉트 D — 완성 모습을 보며 설정하기

### 구조 축

`설정·결과 분할 / 결과 우선 / 적용 전 확인 / 작업 로그 복구`

```text

│ [회사 이름________]   │                              │

│ 첫 고객                │ │ 고객: 입력 대기           ││
│ [고객 이름________]   │ └──────────────────────────┘│
```

### 진행·재개

- 분할 설정 1면과 적용 확인 1면으로 구성한다.
- 왼쪽 설정에 따라 오른쪽 결과 예시가 바뀐다.
- 선택 카드를 끄면 적용 대상에서 제외한다(Draft).
- 적용 전 초안과 미완료 항목을 시작 설정에서 다시 불러온다.

### 실패·복구

- 결과 로그를 `Workspace+Owner / 초대 / 고객+업무` 작업 단위로 표시한다.
- 미리보기는 저장 완료 표시를 사용하지 않는다.
- 서버 결과가 미리보기와 다르면 서버 결과를 정본으로 다시 렌더하고 차이를 설명한다.
- 모바일에서는 좌우 화면을 그대로 축소하지 않고 설정→요약 순차 구조로 바꾼다.

### 장점·위험

- 장점: 무엇이 만들어지는지 저장 전에 가장 명확하게 이해한다.
- 위험: 1인 대표와 모바일 사용자에게 구조가 과할 수 있다.
- 숨은 계약 위험: 미리보기가 실제 저장을 보장하는 것처럼 보이거나 부분 적용 의미가 불명확할 수 있다.

### D안 수용조건

- 미리보기, 저장 중, 서버 저장 완료 상태가 혼동되지 않는다.
- 360px 모바일에서도 결과 우선 철학을 잃지 않는다.
- 작업 단위 실패 뒤 재시도가 성공 작업을 중복하지 않는다.

## 10. 테스트와 수용조건

### 10.1 공통 기능 수용조건

- [ ] 대표 혼자 팀원 정보 없이 Workspace를 시작할 수 있다.
- [ ] 대표가 팀장·사원을 선택적으로 초대할 수 있다(Draft 결정 반영 후).
- [ ] 초대받은 팀장·사원은 회사 생성 화면을 보지 않는다.
- [ ] 첫 고객과 첫 업무는 함께 생성되거나 함께 실패한다.
- [ ] 초대 실패가 Workspace와 첫 고객·업무를 손상시키지 않는다.
- [ ] 같은 제출을 반복해도 중복 데이터가 생기지 않는다.
- [ ] 중단·새로고침·로그아웃 뒤 마지막 안전 지점에서 재개한다.
- [ ] 건너뛴 선택 항목을 오늘 화면에서 다시 찾을 수 있다.
- [ ] 현재 회사·역할·다음 행동을 10초 안에 설명할 수 있다.
- [ ] 정상 경로는 로그인 뒤 3분 안에 오늘 화면의 실제 첫 업무에 도달한다.

### 10.2 시각·접근성 수용조건

- [ ] 한 화면의 핵심 CTA는 하나이며 행동 결과를 한글로 말한다.
- [ ] 데스크톱과 360px 모바일에서 필수·선택·완료·오류가 구분된다.
- [ ] 키보드만으로 입력, 건너뛰기, 재시도, 재개가 가능하다.
- [ ] 포커스 이동과 오류 연결이 DOM 순서와 일치한다.
- [ ] 로딩, 빈 상태, 권한 없음, 오류, 취소·되돌리기, 다음 화면을 비교할 수 있다.
- [ ] 라이트·다크 모두 MoaWork 토큰을 사용하고 상태를 색만으로 전달하지 않는다.

### 10.3 숨은 계약 검수조건

- [ ] 다른 Workspace 식별자를 넣어도 조회·쓰기가 거부된다.
- [ ] 마지막 Owner를 변경·강등·삭제할 수 없다.
- [ ] 진행 상태와 재시도 키가 tenant별로 격리된다.
- [ ] 미리보기·클라이언트 캐시보다 서버 저장 결과가 우선한다.
- [ ] 실제 고객정보·초대정보·비밀값이 로그, 예시, 목업에 남지 않는다.

### 17.1 변경 이유와 Blindspot

고객사는 0에서 시작하는 신규 조직만이 아니다. Monday나 기존 도구에서 고객사와 진행 업무를 이미 관리하고 있을 가능성이 높으며, 이 경우 첫 가치는 제품이 임의의 업무를 만드는 것이 아니라 **기존 고객사와 현재 진행 업무를 손실·중복·오배정 없이 옮겨 오늘 업무를 계속하게 하는 것**이다.

```text

     안전한 미리보기 → 필드 매핑 → 오류·중복 확인 → Owner 최종 적용

3-B. 빈 화면에서 시작
     오늘 홈 → 새 고객·업무는 사용자가 필요할 때 직접 생성
```

단계별 화면 계약은 다음과 같다.

1. `회사 만들기`: Workspace+보호 Owner 생성만 다룬다.
2. `시작 방법 선택`: 세 선택지를 같은 위계로 제공하되 기존 Monday 사용자의 빠른 이해를 위해 `Monday CSV`에 권장 표식을 붙인다.
3. `가져오기`: 이 온보딩이 import를 직접 성공 처리하지 않고 `SAFE-IMPORT-CONTRACT-01`의 dry-run 미리보기·필드 매핑 흐름으로 명확히 handoff한다.
4. `빈 화면에서 시작`: 가짜 고객·기본 업무를 만들지 않고 오늘 홈으로 이동한다.
5. `팀 초대`: 오늘 홈의 후속 checklist에서 언제든 시작·재개하며 온보딩 blocker가 아니다.

### 17.4 임의 업무 생성 금지

- `첫 연락하기`, `오늘`, `현재 사용자 담당` 같은 임의 기본 업무를 자동 저장하지 않는다.
- import된 업무명은 원본 파일의 업무명만 사용한다.
- 원본에 업무명이 없으면 제품이 이름을 만들어 채우지 않고 필수값 오류 또는 사용자 확인 상태로 둔다.
- 기존 업무와 고객사 연결을 확정할 수 없으면 다른 고객사에 자동 연결하지 않고 `미연결` 경고 상태로 둔다.
- 빈 화면에서 시작한 사용자의 새 고객·업무는 사용자가 오늘 홈에서 추후 직접 생성한다.
- 목업 예시는 실제 생성·저장된 업무처럼 표현하지 않는다.

### 17.5 Safe import 불변계약

새 B의 import handoff는 `SAFE-IMPORT-CONTRACT-01`의 다음 경계를 그대로 유지한다.

1. 실제 적용 전 dry-run 미리보기
2. 필수 컬럼 자동 매핑과 애매한 필드의 사용자 확인
3. 행 단위 한글 오류·경고·확인 필요 상태
4. 확정 중복과 유사 중복 분리, 자동 병합 금지
5. 담당자 미매핑 시 `미지정`, 임의 회원 자동 생성·초대 금지
6. 치명 오류가 남아 있으면 최종 적용 차단
7. 적용 전 전체 취소와 동일 요청 멱등성
8. 고객 Owner만 최종 적용
9. 적용 후 rollback 가능 범위와 충돌 미리보기
10. 서버 session의 Workspace tenant 문맥 우선, 파일의 조직 값 신뢰 금지

`Owner 최종 적용` 전에는 미리보기·매핑·오류 정리가 실제 고객사나 업무를 생성한 것처럼 보이면 안 된다. rollback은 적용 전 취소와 구분하며, 적용 뒤 수정된 레코드를 무조건 덮어쓰는 것으로 약속하지 않는다.

### 17.6 Monday·파일 형식 약속 경계

- MVP의 정확한 표기는 `Monday CSV`다.
- Monday OAuth/API 직접 연결, 지속 동기화, 자동 업데이트는 별도 사용자 결정·보안 계약·writer gate 전에는 약속하지 않는다.
- `일반 CSV·엑셀`은 시작 방법 선택지로 보여주되 T02가 실제 허용 확장자, 시트 선택, 수식·날짜·인코딩 처리 계약을 확정하기 전 `.xlsx` 직접 처리를 성공 기능처럼 표현하지 않는다.
- 지원되지 않는 파일은 업로드 성공이나 import 성공으로 가장하지 않고 지원 형식 안내와 안전한 다음 행동을 보여준다.

### 17.7 Downstream delta
