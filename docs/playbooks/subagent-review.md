# 서브에이전트 자체 검수 — 표준안

**발효 2026-08-11 · 소유 MW-총괄 · 정본 코멘트 BBE-94「검수 2단 체계」**

---

## 왜 이 문서가 있나

열린 PR 이 23개까지 쌓였는데 전담 검수는 2칸이었다. 만드는 속도가 검수 속도를 크게 앞질렀다.

그런데 그날 실제로 잡힌 결함 4건은 **전부 «자기» 또는 «옆 세션»** 이 잡았다.

| 결함 | 잡은 쪽 |
| --- | --- |
| 멱등키에 `txid_current()` — 돈이 새는 결함 | 옆 세션 (경계 대조 중) |
| D44 「grep 0건」이 오탐이었음 | 만든 세션 **자기가** |
| 되돌리기가 «빈값→규칙값» 을 못 되돌림 | 만든 세션 **자기가** |
| 정본 파일이 원격에 없음 | 착수하려던 세션 **자기가** |

전담 검수가 낸 것은 PASS 3건뿐. **병목은 만들면서 발견은 못 하고 있었다.**

그래서 검수를 두 단으로 가른다.

---

## 1단 · 서브에이전트 자체 검수 — 전 PR 필수

PR 을 올린 세션이 **자기 서브에이전트를 띄워** 검수한다.
기계로 확인되는 것만 본다. 판단 여지가 적은 영역이라 서브에이전트가 잘한다.

### ★ 성립 조건 — 여기가 무너지면 나머지는 형식일 뿐이다

**서브에이전트 프롬프트에 부모의 결론·변명을 한 줄도 넣지 않는다.**

```
❌  "내가 이렇게 구현했고 다 맞으니까 확인만 해줘"
❌  "이 부분은 의도한 거야"
❌  "CI 통과했으니 문제없을 거야"

✅  "이 diff 와 이 명세를 대조해라. 만든 사람의 설명은 주지 않는다"
```

서브에이전트는 새 문맥으로 시작한다. 부모가 자기 해석을 넣지 않으면 **명세를 처음 읽는 사람**이 된다.
그게 이 방식이 독립 검수로 성립하는 이유다. 유도 문장이 들어가면 그 검수는 **무효**다.

### 부모 세션이 지킬 것

- 서브에이전트에 주는 것: **명세**(dump 출력 · 결정대장 · 카드 본문) + **diff**. 그게 전부다
- 결과는 **그대로** BBE-94 와 PR 코멘트에 붙인다. **요약하지 마라** — 요약하는 순간 부모 해석이 섞인다
- **자기 PR 을 자기가 GitHub approve 하지 않는다.** 1단은 «판정과 기록» 까지다.
  승인 클릭은 전담 검수 또는 MWC 가 한다. 누가 통과시켰는지 흔적이 남아야 한다

## 2단 · 전담 독립 검수 — 아래 넷 중 하나라도 걸리면

되돌리기 어렵거나 돈이 나가는 것만. **상대 진영**이 본다(C가 만들면 G, G가 만들면 C).

```
① 돈       발송·과금이 걸린다            → 멱등을 «실제로 두 번 눌러» 확인
② 비가역   supabase/migrations/ 에 파일 추가
③ 권한     D24 조회 범위에 닿는다        → 뷰·필터·검색·대시보드·권한 매트릭스
④ 구조     프리셋·컬럼·아이템 «정의» 를 건드린다  → D73 비우기 vs 지우기
```

**왜 2단만 상대 진영인가** — 서브에이전트는 부모와 같은 모델이다.
명세 자체가 애매하면 둘 다 같은 쪽으로 읽는다. 진영이 다르면 읽는 방식이 달라서 그때 걸린다.

**자체 승격**: 1단 검수 중 위 조항이 발견되면 **스스로 2단으로 올린다.**
PASS 를 내지 말고 「2단 승격 필요: <사유>」로 보고한다.

## 붙여넣는 프롬프트

세션이 서브에이전트에 그대로 넣는다. `<>` 만 채운다.

```
너는 독립 검수자다. 이 PR 을 만든 사람의 설명은 받지 않았고, 앞으로도 받지 않는다.
명세와 diff 만 보고 판정해라.

대상   PR #<번호> · 카드 <BBE-xxx> · 브랜치 <브랜치명>

■ 먼저 할 것
  git fetch origin && git rebase origin/main
  gh pr diff <번호>                        ← 이것이 네가 볼 «전부» 다
  node docs/design/dump-mockup.mjs [탭]    ← 명세. 맨 위 경고문도 읽어라
  docs/handoff/결정대장.md 에서 이 카드가 덮는 D번호

■ 8개를 «명령 출력» 으로 증명해라. 문장으로 쓰지 마라.

 1  bash scripts/check.sh            → 초록인가
 2  node docs/design/qa-mockup.mjs   → 86개인가 (55·75면 base 가 낡았다. FAIL)
 3  구조 축소 (D73)
      착수 전후 컬럼 수 · 아이템 종류 · 자동 이동 규칙 개수를 «숫자로» 비교
      하나라도 줄었으면 무조건 FAIL. «비우기» 지 «지우기» 가 아니다
 4  git grep -n app_admins -- app/src   → 직접 select 0건인가
 5  리스 위반
      gh pr diff --name-only 결과가 선언한 리스 밖으로 나갔나
 6  값 잔존 (해당 시)
      셀을 고치고 새로고침 → 값이 남는가. «에러 없음» 은 근거가 아니다
 7  NOT_RUN 위장
      못 돌린 항목을 PASS 로 적어놨나. 스크린샷·health 는 NOT_RUN 이 정상이다
 8  목업 1:1 대조
      dump 출력과 나란히 놓고 «같아 보인다» 가 아니라 «같게 동작하나»

■ 2단 승격 — 아래 중 하나라도 걸리면 즉시 멈추고 보고해라
    ① supabase/migrations/ 에 파일 추가
    ② 발송·과금이 걸린다
    ③ D24 조회 범위에 닿는다 (뷰·필터·검색·대시보드·권한)
    ④ 프리셋·컬럼·아이템 «정의» 를 건드린다
  → 「2단 승격 필요: <사유>」 로 보고. 네가 PASS 내지 마라.

■ 판정
  PASS  8개 전부 근거 있음 + 2단 조항 0개
  FAIL  하나라도 실패. 무엇을 어떻게 고쳐야 하는지까지 적어라
  ※ GitHub approve 는 누르지 마라. 판정과 근거만 낸다.

■ 출력 형식
  항목별 [PASS/FAIL/NOT_RUN] + 실제 명령 출력 붙여넣기
  마지막 줄: 종합 판정 한 줄
```

## 시각 검수가 불가한 동안 (한시 규칙)

`app/.env.local` 부재 · Vercel Preview SSO 보호로 스크린샷·`/login` health 를 못 찍는 세션이 많다.
**자격증명을 지어내지 않고 NOT_RUN 으로 남기는 것이 옳다.**

- 코드·데이터 게이트(check.sh · CI · 1단 8항목 · grep 증명)만으로 머지 판정한다
- 스크린샷·health 는 **NOT_RUN** 으로 명시하고 머지를 막지 않는다. **PASS 로 위장하지 마라**
- 접근권이 열리면 BBE-131 이 한 번에 몰아서 시각 확인한다
- 이 예외는 «화면이 바뀌는 카드» 에만 적용한다. **로직 회귀는 여전히 값으로 증명해야 한다**
